## Purpose

Issue #51 makes the `GroupPlan` contract from issue #50 usable by a teacher
without creating operational collaboration state.

The implemented authoring paths are:

```text
manual GroupPlan authoring
direct student_id,group CSV arrangement import
```

Both paths converge on the same native `GroupPlan` representation and the same
edit, preview, approval, and cancellation lifecycle.

The critical boundary remains:

```text
GroupPlan != Group
PlannedGroup != Group
planned_group_key != group_id
GroupPlan approval != Group creation
```

Canonical `Group` and `GroupMembership` creation is now implemented exclusively
by issue #56 after separate preview and approval. See
`v0.3.0-group-plan-application.md`.

## Teacher-controlled manual authoring

A manual plan starts with:

```text
strategy: manual
status: draft
seed: none
signal binding: none
roster_student_ids: exact current Core roster
unresolved_student_ids: every currently unassigned roster student
```

The caller supplies a stable `group_plan_id`. Concord validates that identity
using Core's identifier rules and binds the plan to the exact Class and Activity.

Teachers may then:

- add a plan-local group;
- edit its label, description, or optional Effective Context;
- remove it;
- place a roster student into a planned group;
- move a roster student from one planned group to another;
- return a student to the unresolved set; and
- explicitly refresh the plan against the current Core roster.

`planned_group_key` is stable plan-local identity. Editing a group's
teacher-facing metadata does not replace or re-key that group.

Removing a planned group never redistributes students automatically. Its assigned
students become unresolved.

## Student identity and placement

Placement uses exact Core `student_id` values only.

Concord does not use:

```text
student name
email address
roster position
case-folded identity
trimmed identity
fuzzy matching
```

A student may appear in at most one `PlannedGroup`.

Moving a student from group A to group B is one guarded GroupPlan revision. The
service removes the student from the prior group and adds the student to the
destination in the same replacement transaction.

Placing a student into the group where that student is already assigned is an
exact no-op. Unassigning a student who is already unresolved is also an exact
no-op. Neither action creates native history or a new Activity-work snapshot.

## Editing generated or imported plans

Issue #52 now implements the deterministic `random` origin described by this
editing contract. Random plans use these same draft/previewed edit operations,
and ordinary teacher edits preserve their original seed and size/count target
rather than converting the plan to `manual`.

The manual editor is not restricted to plans whose strategy is `manual`.

A draft or previewed plan created by a later random or signal-backed planner may
use the same edit operations. Ordinary manual editing preserves the plan's
origin metadata:

```text
strategy
target_group_size / target_group_count
seed
source_signal_set_id
source_signal_set_digest
source_signal_dimension_id
```

Editing therefore does not relabel a random or signal plan as a manual plan.

Direct arrangement replacement is different by definition: replacing a plan
from an arrangement CSV changes the strategy to `imported_arrangement` and
clears generator-specific target, seed, and signal-binding metadata.

## Draft and preview editing

Issue #50's typed full-proposal replacement service remains the canonical write
boundary beneath #51.

A material authoring change:

- preserves the stable `group_plan_id`;
- preserves original creation provenance;
- creates one immutable native GroupPlan revision;
- creates one guarded Activity-work snapshot revision;
- records update provenance;
- recomputes exact grouped/unresolved coverage; and
- leaves the resulting plan in `draft`.

Editing a `previewed` plan therefore returns it to `draft` and clears preview
provenance from current state. The historical previewed revision remains in the
immutable native history.

`approved`, `applied`, and `cancelled` plans reject ordinary authoring changes.

## Roster drift and explicit refresh

Targeted editing is fail-closed when the Core roster has changed since the
current GroupPlan revision.

For ordinary add/edit/remove/place/unassign operations:

```text
stored roster snapshot != current Core roster
    -> conflict
    -> no GroupPlan write
```

Concord does not silently absorb a new roster while performing an unrelated
edit.

Roster refresh is an explicit operation. It:

- rereads the current Core roster;
- preserves placements for students still on the roster;
- removes departed students from proposed groups;
- adds newly rostered students to `unresolved_student_ids`;
- preserves empty planned groups;
- preserves strategy, target, seed, and signal-binding metadata;
- creates one new draft GroupPlan revision; and
- changes `previewed` back to `draft`.

If the roster is unchanged, refresh is an exact no-op.

## Arrangement CSV v0.3

The direct arrangement import contract is intentionally narrow.

Exact header:

```csv
student_id,group
```

Example:

```csv
student_id,group
student-001,group-a
student-002,group-a
student-003,group-b
```

Parsing rules:

- encoding is UTF-8;
- an initial UTF-8 BOM is accepted through `utf-8-sig`;
- Python CSV quoting semantics apply;
- delimiter sniffing is not performed;
- the header is exact and case-sensitive;
- the header contains exactly two columns;
- each data row contains exactly two fields;
- blank physical lines may be ignored;
- at least one data row is required.

### `student_id`

The value must:

- be nonblank;
- contain no leading or trailing whitespace;
- satisfy Core identifier validation;
- exactly match a student in the current Core roster; and
- occur at most once in the CSV.

Concord does not trim, case-fold, normalize, infer, or fuzzy-match the value.

A duplicate student row is invalid even when both rows name the same group.

### `group`

The value must:

- be nonblank;
- contain no leading or trailing whitespace;
- satisfy the PDS identifier alphabet of letters, numbers, `_`, and `-`; and
- be interpreted case-sensitively.

The exact token becomes both the initial `planned_group_key` and initial label.

Repeated exact group tokens coalesce into one `PlannedGroup`. Concord does not
slugify the token.

A roster student omitted from the CSV remains unresolved. An empty `group` cell
is invalid; unresolved students are represented by omitting their rows.

## Deterministic normalization

Arrangement parsing is independent of row ordering.

For the same student-to-group mapping:

- proposed groups are ordered by `planned_group_key`;
- each `PlannedGroup` canonicalizes its student IDs; and
- unresolved roster student IDs are deterministic.

The parser reports only bounded validation diagnostics. Where a data row caused
the error, diagnostics identify its CSV row number. Diagnostics do not dump
unrelated roster contents.

## New-plan import

`import-arrangement` creates:

```text
strategy: imported_arrangement
status: draft
seed: none
signal binding: none
roster_student_ids: exact current Core roster
```

Assigned students come from the validated CSV and omitted roster students are
unresolved.

Import does not preview, approve, apply, or create canonical Groups.

Concord does not persist the arrangement source path, filename, or raw CSV
bytes in the GroupPlan.

## Existing-plan arrangement replacement

`replace-arrangement` is allowed only for an editable draft or previewed plan.

The entire CSV is decoded and validated before any state mutation. A parse or
validation failure leaves both GroupPlan history and Activity-work snapshot
history unchanged.

A successful replacement:

- preserves `group_plan_id`;
- preserves immutable prior revisions;
- replaces the complete proposed-group arrangement atomically;
- recomputes unresolved roster students;
- sets strategy to `imported_arrangement`;
- clears target, seed, and signal-binding metadata;
- creates one new native revision;
- creates one new Activity-work snapshot; and
- leaves the plan in `draft`.

## Preview and approval

Issue #51 reuses issue #50's lifecycle services.

```text
draft -> previewed -> approved
```

Preview is an explicit persisted mutation. It revalidates the exact current Core
roster before recording the previewed revision.

Approval is a separate explicit mutation. Under the current baseline, approval
requires:

- the exact previewed plan revision to remain current;
- zero unresolved students; and
- at least one nonempty planned group.

Approval creates no `Group` or `GroupMembership`.

There is intentionally no quick-apply path and no `mark_applied` operation in
issue #51. Issue #56 now performs the only atomic:

```text
approved GroupPlan
    + canonical Group/GroupMembership write set
    -> applied GroupPlan
```

## Direct CLI

The noninteractive direct family is:

```text
concord group-plan list
concord group-plan show
concord group-plan create-manual
concord group-plan add-group
concord group-plan edit-group
concord group-plan remove-group
concord group-plan place-student
concord group-plan unassign-student
concord group-plan refresh-roster
concord group-plan import-arrangement
concord group-plan replace-arrangement
concord group-plan preview
concord group-plan approve
concord group-plan cancel
```

Mutating commands require explicit actor context and the exact expected Activity
snapshot. They never prompt.

Output identifies the record as a `GroupPlan` and reports status, snapshot, and
compact group/assigned/unresolved counts without dumping the complete roster.

Arrangement success output additionally reports parsed row, proposed-group,
assigned-student, and unresolved-student counts.

Approval output states that canonical Groups were not created.

## Teacher menu

Within an open Activity, `Groups and Participants` now exposes two explicit
paths:

```text
Plan groups
Manage Groups and Memberships
```

The second path is the existing direct operational Group/Membership menu.

The planning submenu is deliberately bounded for issue #51. It provides the
manual/import authoring and lifecycle operations implemented by the shared
workflow services. It does not implement issue #65 guided Activity setup or
issue #66's final integrated menu design.

Teacher-facing names may be displayed for usability, but persisted and mutation
identity remains exact Core `student_id`.

## Direct Group workflow remains first-class

Existing operational Group creation remains independent:

```text
concord group create
concord group member add
concord group member end
concord group list
concord group show
```

These commands do not require a GroupPlan and do not create GroupPlan history.

Likewise, GroupPlan authoring through approval creates no canonical Group or
Membership.

## Privacy and side-effect boundary

Manual planning and arrangement import create no:

```text
Group
GroupMembership
RoleAssignment
ResponsibilityAssignment
ArtifactInstance
ArtifactPage

```

GroupPlan arrangement state is teacher-restricted planning state. It is not
projected into packets, routing payloads, academic results, publication records,
or default support output.

Issue #51 does not consume or emit `grouping_signal_set_v1`. Signal discovery
and import remain issue #53, while signal-backed planners remain issue #54.

Concord still has no Meridian runtime dependency for group planning.
