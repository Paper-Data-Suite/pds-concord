# v0.3.1 generation-wide Packet rendering and reprinting

## Status

Issue #110 defines Concord's v0.3.1 complete-generation Packet rendering and
reprinting contract.

The operation unit is one existing Packet generation, not an independent loop of
standalone Packet renders.

## Generation is the runtime unit

A Packet generation is one Activity-owned class set of target-specific
`PacketInstance` records sharing one exact generation identity.

`render_packet_generation(...)` resolves that generation from one exact verified
Activity snapshot and renders every eligible target in stable target order.

The optimized generation path does **not** call public
`render_packet_instance(...)` once per target. Standalone rendering remains
public and uses the same lower-level deterministic Packet rendering authority.

The source snapshot remains fixed for the logical operation. Rendering one target
does not advance the source semantics used for later targets.

## Exact render context

Generation rendering uses an ephemeral operation-scoped render context containing:

- resolved workspace and `ModuleWorkRef`;
- the Standards library required by the Activity;
- exact source snapshot revision and SHA-256;
- one verified `ConcordRecordGraph`;
- Artifact and Artifact Page indexes;
- an operation-local cache of exact immutable Template/layout dependencies.

The context is not persistent cache state. It creates no SQLite cache, render
queue, background job, or new canonical record type.

Full Activity graph materialization is O(1) with respect to Packet target count.

The qualified 1, 10, and 30 target cases each use one full Activity graph
materialization. A separate bounded current-pointer read is allowed for the
last-safe-point currentness check.

## Reviewed-snapshot currentness

Teacher selection uses the read-only `PacketGenerationSummary` projection.

The projection carries both:

- `snapshot_revision`;
- `snapshot_sha256`.

`RenderPacketGenerationRequest` accepts optional `expected_snapshot_revision`.

Routine teacher generation rendering passes the reviewed
`PacketGenerationSummary.snapshot_revision` into the renderer. The direct
`concord packet generation-render` command first resolves the same generation
projection and uses the same currentness authority.

Before the first durable output mutation, generation rendering verifies that the
canonical current pointer still matches the reviewed source revision and SHA.

A stale reviewed generation fails closed before PDF installation.

The final lifecycle reconciliation remains protected by exact expected-snapshot
concurrency.

## Teacher complete-generation workflow

The opened-Activity Packet menu exposes:

```text
Prepare / Generate Packet

1. Preview and generate a Packet
2. List generated Packet Instances
3. Inspect a Packet Instance
4. Render / reprint a complete generation
5. Render / reprint one Packet Instance
6. Resume incomplete route preparation
7. Open a rendered Packet
8. Open rendered Packet folder
```

Routine complete-generation selection is teacher-readable. The primary label uses
Packet name, Session label, Packet count, page count, and lifecycle status rather
than requiring a raw generation UUID.

The raw generation identity remains available to direct CLI and diagnostic
surfaces.

## RENDER and REPRINT semantics

If every target Packet is `generated`, the complete-generation action is
`REPRINT`.

If every target Packet is either `generated` or `rendering`, and at least one
target is still `rendering`, the complete-generation action is `RENDER`.

If any target is `routes_pending`, generation rendering is blocked and the
teacher is directed to `Resume incomplete route preparation`.

Targets in `planned`, `failed`, or `cancelled` are never silently skipped. The
teacher is shown that the generation requires attention and the renderer does not
present a subset as a complete class set.

## Shared immutable dependency reuse

Exact immutable Template/layout dependencies are reused within one generation
operation by:

```text
(template_id, template_version_id)
```

For N Packet targets using K distinct immutable Template Versions, exact
Template/layout resolution scales with K rather than N.

Target-specific rendering values are never cached as shared Template state.

In particular:

```text
Packet target != Artifact Author != Artifact Subject
```

unless the canonical records independently make those identities equal.

Issue #113 relationship-aware reviewer/reviewee/observer rendering values remain
per target and per Artifact binding.

## Deterministic rendering parity

Standalone and generation rendering share the same lower-level Packet rendering
mechanics.

For identical exact source state they preserve the same:

- PDF bytes;
- SHA-256;
- output path;
- page count and page order;
- route count;
- PDS2 payload identities and ordering;
- Template Version;
- frozen rendering values.

Historical v1 starter rendering and current relationship-aware v2 starter
rendering therefore remain governed by the exact stored Template Version and
Packet binding rather than today's mutable current Template pointer.

## Route identity and route validation

Reprint allocates zero replacement routes.

Existing Packet, Artifact, Artifact Page, route ID, Core RouteRegistration, and
PDS2 payload identities remain authoritative.

Every route-bearing physical page still loads and authenticates its exact
immutable Core RouteRegistration. Shared Template reuse never permits one
target's route identity to stand in for another target's route.

`routes_pending` recovery remains a separate authority and is not hidden inside
rendering.

## Generated-path compatibility

Issue #124 remains authoritative for Packet output paths.

Fresh Packet renders continue to use:

```text
rendered/packets/cgo_<24hex>.pdf
```

through the shared generated-path authority.

Historical `output_relative_path` values remain authoritative on replay. #110
does not rename or migrate prior rendered files.

Existing different bytes at an expected output path continue to fail closed; the
renderer never silently overwrites them.

## Lifecycle reconciliation and partial success

A healthy first render prepares and installs target PDFs in deterministic target
order and performs one bounded canonical lifecycle reconciliation for the
generation.

For the qualified 1, 10, and 30 target structural cases:

```text
full Activity graph materializations = 1
current-pointer currentness reads = 1
generation lifecycle commits = 1
```

A completed reprint with no lifecycle changes performs no canonical lifecycle
commit.

Filesystem durability and canonical lifecycle state are intentionally distinct.

If target K fails after K-1 outputs become durable,
`PacketGenerationRenderPartialSuccessError` identifies the exact completed output
set.

If every intended PDF is durable but the final lifecycle reconciliation fails,
`PacketGenerationLifecyclePartialSuccessError` reports durable outputs while
truthfully identifying incomplete canonical lifecycle reconciliation.

Retry reuses deterministic output identities and does not allocate replacement
routes.

## Memory boundary

Generation rendering processes one target's render images at a time.

The generation accumulator retains completed result metadata and deferred
canonical lifecycle updates. It does not retain every target's page-image
collection for the whole class set.

## Existing output opening

Issue #101 remains the verified local-open authority.

After generation rendering/reprinting, teachers continue to use:

- `Open a rendered Packet`;
- `Open rendered Packet folder`.

`rendered/packets/` remains a teacher-local viewing/printing directory, not a
share-safe distribution package.

## Attention and recovery

Existing Prepare attention semantics remain authoritative:

- `concord_prepare_materials`;
- `concord_prepare_routes_pending`;
- `concord_prepare_recovery`.

Issue #110 adds no render queue, progress record, or second attention model.

- change PDS2;
- allocate replacement routes during reprint;
- repair routes as a rendering side effect;
- merge a generation into one aggregate PDF;
- turn rendered Packet output into a share/distribution package;
- implement Issue #114 feedback distribution;
- add printer-driver integration;
- persist a render cache;
- add background rendering;
- calculate Grades;
