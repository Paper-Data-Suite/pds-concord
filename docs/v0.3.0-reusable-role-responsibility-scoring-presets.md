# v0.3.0 reusable Role, Responsibility, Criterion Set, and Scoring Scale presets

**Status:** Implemented for issue #64

## Purpose

Issue #64 adds four workspace-level reusable preset authorities to Concord:

- Role presets;
- Responsibility presets;
- Criterion Set presets; and
- Scoring Scale presets.

The implementation follows one hard rule:

```text
reusable preset / exact preset revision
    -> explicit teacher selection
    -> target-context validation
    -> fresh native target state
```

It does not make an earlier Activity the authority for later Activities, and it
does not introduce live inheritance.

The corresponding distinctions are normative:

```text
Role preset != RoleAssignment
Responsibility preset != ResponsibilityAssignment
Criterion Set preset != Activity Criterion Set revision
Scoring Scale preset != Activity Scoring Scale revision
Score != reusable configuration
```

The teacher-facing objective is selection-oriented reuse. Storage roots, immutable
revision identifiers, materialization, target-ID rewriting, and review digests are
implementation details rather than routine teacher concepts.

## Canonical authority and storage

Presets are Concord-owned workspace-level reusable state. They are not class-
scoped and are not stored beneath any Activity `ModuleWorkRef`.

The canonical library root is below shared Concord workspace state:

```text
shared/concord/reusable-presets/
    roles/
    responsibilities/
    criterion-sets/
    scoring-scales/
```

The implementation uses `concord_reusable_preset_library_v1` canonical storage
with strict deterministic JSON, immutable revision files, a guarded current
pointer, exact content SHA-256 verification, validated identifiers, safe path
containment, create-only lineage creation, and explicit stale-revision conflicts.

Read-only discovery does not create the workspace or preset folders.

Malformed canonical state fails closed. Unknown canonical fields are rejected.
Ordinary reads never repair or silently discard corrupt preset state.

## Immutable revision model

Each preset has a stable `preset_id` lineage and immutable saved versions with
fresh `preset_revision_id` values:

```text
preset_id
    revision 1
    revision 2
    revision 3
```

A teacher-facing edit means “save a new version.” It never rewrites an earlier
canonical revision.

Retirement is another immutable successor revision with `status="retired"`.
Retired presets remain inspectable but disappear from ordinary active selection.

Changing or retiring a preset never modifies Activity-native state that was
materialized earlier.

## Role preset contract

A Role preset contains reusable Role semantics only:

- preset identity and immutable revision metadata;
- teacher-facing name;
- `role_key`;
- optional role label;
- optional reusable description;
- optional applicability hints;
- fresh preset provenance.

It never contains:

- `role_assignment_id`;
- student or participant identity;
- `membership_id`;
- Activity-specific `group_id`;
- Session identity;
- `EffectiveContext`;
- assignment status/history;
- `assigned_by` from a prior assignment;
- contribution, authorship, evidence, or Score state.

Applying a Role preset produces one fresh `RoleAssignment` through the normal Role
authority. The teacher supplies the fresh participant, optional Group/Membership,
Effective Context, assignment ID, actor, and target Activity.

## Responsibility preset contract

A Responsibility preset contains:

- preset identity and immutable revision metadata;
- teacher-facing name;
- reusable obligation/description text;
- optional expected output;
- optional applicability hints;
- fresh preset provenance.

It never contains prior assignee, Group, work item, Effective Context, assignment
status, StatusReason, assignment provenance, supersession history, contribution
claims, performance judgment, or Score state.

Applying a Responsibility preset creates one fresh `ResponsibilityAssignment`
through the ordinary Responsibility authority.

## Criterion Set preset contract

A reusable Criterion Set preset is not an Activity-native `CriterionSet` record.
It stores the semantic configuration needed to construct fresh Activity-native
records:

- stable preset lineage and immutable revision identity;
- teacher-facing name and purpose;
- `criterion_set_kind`;
- optional Core `standards_profile_id`;
- deterministic ordered Criterion definitions;
- Criterion key, label, definition, and kind;
- supported target kinds;
- exact Core `standard_id` where standard-backed;
- `alignment_standard_ids`;
- optional reusable Scoring Scale preset recommendation.

Preset Criteria do not use the future target Activity's `criterion_id` or
`criterion_set_id` as reusable identity.

Application creates:

- a fresh Activity-native `CriterionSet`;
- fresh ordered native `Criterion` records;
- optionally one fresh Activity-native `ScoringScale`;
- an updated Activity selection containing the fresh Criterion Set.

The resulting Activity graph is self-contained and does not require the preset
library to interpret historical Scores later.

## Scoring Scale preset contract

A Scoring Scale preset stores reusable Scale semantics:

- stable preset lineage and immutable revision identity;
- teacher-facing name;
- `scale_type`;
- ordered exact `ScoringScaleLevel` values, labels, meanings, positions, and
  descriptions;
- optional intended use;
- optional aggregation guidance.

Exact native value typing is preserved. For example:

```text
1
1.0
true
"1"
```

remain distinct when the native Scoring Scale contract distinguishes them.

Application creates a fresh Activity-native `ScoringScale` with a fresh
`scoring_scale_id`, fresh Activity-native lineage, and fresh target provenance.

## Criterion-to-Scale recommendation

Criterion Set and Scoring Scale presets remain separate authorities.

A Criterion preset may recommend one exact reusable Scale preset revision. The
recommended Scale is a convenience, not a lock and not a Score suggestion.

At application time the teacher may:

- accept the recommended Scale;
- choose another active saved Scale; or
- continue without materializing a Scale when the Criterion configuration permits
  that choice.

When a Scale is materialized, Concord rewrites each target native Criterion's
`default_scoring_scale_id` to the newly created Activity-native Scale ID.

A workspace-level Criterion preset never stores another Activity's native
`scoring_scale_id`.

## Core standards validation

Core remains authoritative for standards.

Standard-backed Criterion presets are validated against the current Core
standards library at create/revise time when standards references are present,
and again against the target Activity at application time.

Application rejects before write when:

- the Core standards library required by the preset is unavailable;
- the preset profile does not resolve;
- a referenced Standard does not resolve;
- a referenced Standard is inactive;
- the preset profile differs from the target Activity profile;
- a standard-backed Criterion is not one of the target Activity Focus Standards;
- the target Activity scoring orientation rejects the Criterion kind.

Concord never silently substitutes another Standard, maps by similar code, drops
a Criterion, or changes the Activity Focus Standards to make a preset fit.

## Score boundary and historical stability

`ScoreRecord` and `ScoreEvidenceLink` are absolute preset exclusions.

Preset storage never contains:

- Score IDs;
- Score target;
- Score value or disposition;
- scorer identity;
- scored timestamp;
- Score basis or rationale;
- moderation state;
- Score Evidence Links;
- evidence locator;
- prior Score correction/supersession history.

Applying or revising presets creates zero Scores.

Once an Activity-native Criterion/Scale configuration is used by a Score, later
preset revision or retirement cannot alter those native records. Historical Score
validation remains bound to the exact Activity-native Criterion and Scale
revisions under which the Score was recorded.

## Zero-write preparation and exact commit

Preset application uses an explicit prepare/review/commit boundary.

The application preparation functions are:

```text
prepare_role_preset_application
prepare_responsibility_preset_application
prepare_scoring_setup
```

Preparation:

- resolves the exact preset revision;
- validates active/usable status;
- loads and validates the exact target Activity graph;
- validates fresh target identities;
- constructs the exact candidate native records;
- validates the prospective native graph;
- validates Core standards where required;
- computes a deterministic `review_digest`;
- performs zero canonical writes.

Commit functions rerun preparation and require the exact reviewed digest:

```text
apply_role_preset
apply_responsibility_preset
materialize_scoring_setup
```

A stale preset revision, target Activity snapshot, target identity collision,
standards mismatch, or changed reviewed semantics fails before canonical write.

Composed Criterion Set + Scoring Scale application is one guarded Activity batch,
so Concord cannot publish only the Scale and then fail halfway through Criterion
materialization.

## Save existing configuration as a preset

Teachers may deliberately save reusable semantics from existing native state.
This is extraction through a positive allowlist, not record copying.

The zero-write preparation functions are:

```text
prepare_role_preset_from_assignment
prepare_responsibility_preset_from_assignment
prepare_scoring_scale_preset_from_activity
prepare_criterion_set_preset_from_activity
```

The reviewed commit functions are:

```text
save_role_preset_from_assignment
save_responsibility_preset_from_assignment
save_scoring_scale_preset_from_activity
save_criterion_set_preset_from_activity
```

Every preview identifies reusable fields and `excluded_state` explicitly and
returns a deterministic `review_digest`.

For Role extraction, Concord copies only the reusable role key/label semantics
plus teacher-supplied preset metadata. It excludes assignee, Membership, Group,
Effective Context, lifecycle, history, and assignment provenance.

For Responsibility extraction, Concord copies reusable responsibility and
expected-output text plus teacher-supplied preset metadata. It excludes assignee,
Group/work-item context, lifecycle, history, and provenance.

For Scoring Scale extraction, Concord copies exact Scale type/levels/guidance but
not native Scale identity, lineage, revision, supersession, Activity context, or
Score state.

For Criterion Set extraction, Concord copies ordered reusable Criterion semantics
and Core standards references but not native Criterion/Set identities, Activity
selection, Score history, or native Scale IDs.

If the source native Criteria refer to an Activity-native Scale, the teacher must
explicitly map that recommendation to an existing reusable Scoring Scale preset.
Otherwise the native Scale reference is visibly excluded rather than promoted to
cross-Activity authority.

Unrelated operational Activity changes do not invalidate a save review when the
exact reusable source semantics being saved have not changed.

## Teacher-facing workflow

The main Concord menu includes a workspace-level `Reusable Presets` area with:

```text
1. Roles
2. Responsibilities
3. Criterion Sets
4. Scoring Scales
```

Each family exposes teacher-language operations:

```text
View saved presets
Create a preset
Edit a preset
Retire a preset
```

“Edit” creates a fresh immutable successor internally. Routine screens do not use
storage-root, lineage-head, materialization, or snapshot-pointer terminology.

Normal Role assignment offers:

```text
Use a saved Role
Enter Role manually
```

Normal Responsibility assignment offers:

```text
Use a saved Responsibility
Enter Responsibility manually
```

The scoring menu composes Criterion and Scale selection into one task:

```text
Use Saved Scoring Setup
```

The teacher chooses saved Criteria, sees the recommended Scale when present, may
choose another compatible saved Scale, reviews the setup, and confirms. Concord
then creates fresh native configuration and reports `Scores created: 0`.

The existing manual Role, Responsibility, Criterion Set, Scoring Scale, and Score
workflows remain first-class fallbacks.

All new menu surfaces preserve H/B/M/Q behavior and normal confirmation
semantics. Cancellation before final confirmation writes no canonical state.

## Direct CLI

The direct CLI is deterministic and noninteractive.

Workspace-level management commands are:

```text
concord role-preset list|show|validate|create|revise|retire
concord responsibility-preset list|show|validate|create|revise|retire
concord criterion-preset list|show|validate|create|revise|retire
concord scale-preset list|show|validate|create|revise|retire
```

Fresh application uses reviewed preview/commit pairs:

```text
concord role-preset apply-preview|apply
concord responsibility-preset apply-preview|apply
concord criterion-preset apply-preview|apply
```

Safe save-from-existing uses reviewed preview/commit pairs:

```text
concord role-preset save-preview|save
concord responsibility-preset save-preview|save
concord criterion-preset save-preview|save
concord scale-preset save-preview|save
```

Direct write commands require explicit actor context. Activity-native application
requires exact target Activity snapshot concurrency. Preset revision/retirement
requires the exact current preset revision.

## Relationship to issue #48

Issue #48's boundary remains normative:

> Reuse means reuse of definitions, references, or starting values. It does not
> mean reuse of an earlier Activity's canonical identities, assignments,
> evidence, judgments, routes, publications, or history.

Issue #64 supplies the workspace-level authority that #48 intentionally deferred.
The older Activity-native `CriterionSet.scope="reusable"` remains semantic
metadata; it is not retroactively reinterpreted as the global preset library.

No migration scans existing Activities or automatically promotes historical
`scope="reusable"` records.

## Relationship to issue #63

Safe Activity copying continues to exclude:

```text
criterion_set_ids = ()
RoleAssignments
ResponsibilityAssignments
Activity-native ScoringScale identities
Scores
```

Issue #64 does not weaken that boundary. A later guided copy/setup workflow may
select reusable presets and materialize fresh target state, but it must never copy
source Activity scoring or assignment identities.

## Relationship to Templates and Packets

These remain distinct authorities:

```text
Role preset
Responsibility preset
Criterion Set preset
Scoring Scale preset
TemplateDefinition / TemplateVersion
PacketDefinition / PacketVersion
```

Templates and Packets do not own #64 preset definitions. Later guided setup may
compose them without collapsing their authorities.

## Privacy and data minimization

Reusable preset canonical state forbids operational student and evidence data,
including:

- student IDs/names;
- roster snapshots;
- Membership/Group assignment history;
- grouping-signal values or bands;
- Artifact Authors/Subjects;
- retained scans and source paths;
- Reviews or Moderation history;
- Score values/dispositions/evidence;
- route IDs;
- publication IDs;
- Academic Work Registration IDs;
- copied operational provenance.

Criterion presets may retain exact Core standards references because those are
shared definitions, not student evidence or judgment.
