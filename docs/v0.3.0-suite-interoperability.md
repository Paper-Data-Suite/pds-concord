# v0.3.0 Suite Interoperability and Structural Readiness

**Status:** Implemented for issue #68  
**Development baseline:** `pds-concord 0.3.0.dev0`  
**Core compatibility:** `pds-core>=0.6.3,<0.7`

## Purpose

Issue #68 completes Concord's **module-side** interoperability for future Paper
Data Suite doctor, launcher, owner-routed action, and mixed returned-paper
workflows.

The ownership boundary is:

```text
Paper Data Suite
    -> orchestration, exact release qualification, doctor presentation,
       launching, mixed-intake UX and cross-module aggregation

PDS Core
    -> neutral module-operations contracts, provider diagnostics,
       PDS2 ownership/routing, retained-source custody and dispatch

Concord
    -> structural readiness meaning, teacher attention meaning,
       Concord route handling and Concord-owned domain state
```

This issue does not make the Suite a Concord dependency and does not move
Concord domain semantics into Core.

The durable rule is:

```text
orchestration != ownership
```

## One Core v1 operations profile

Concord continues to install exactly one operations entry point:

```text
paper_data_suite.module_operations
    concord = concord.pds_operations:get_module_operations_profile
```

The current validated profile is equivalent to:

```text
module_id = concord
supported_core_operations_contract_versions = {1}
attention_provider = present
readiness_provider = present
```

Issue #67 originally introduced the same profile with attention only.
Issue #68 extends that profile rather than adding a second provider family.

`concord.pds_operations` remains a thin lazy-loading boundary.

## Readiness question

Concord readiness answers:

> Can Concord meaningfully operate in the exact supplied workspace/class context?

Readiness is deliberately structural:

```text
readiness != attention
readiness != diagnostics
readiness != launchability
readiness != routing
readiness != publication
readiness != Suite release qualification
readiness != teacher priority
```

A teacher can have pending work while Concord is structurally ready.

## Evaluated versus unavailable

Core v1 supports two readiness evaluation states:

```text
evaluation = evaluated
ready = True | False
```

and:

```text
evaluation = unavailable
ready = None
```

The distinction is semantic.

`ready=False` means Concord safely inspected enough authoritative state to
establish a concrete structural problem.

`evaluation="unavailable"` means Concord could not safely or authoritatively
inspect enough state to answer.

Do not convert unreadable or unsafe state into a false `ready=False`.

## Explicit workspace requirement

The shared module-operations request must carry an explicit `workspace_root`.

Missing explicit workspace produces:

```text
evaluation = unavailable
ready = None
notice = concord_readiness_unavailable
```

The readiness provider does not fall back to:

```text
PDS_WORKSPACE_ROOT
saved workspace configuration
the user's default workspace
```

and it never creates or repairs a workspace.

Readiness inspection is observational.

## Workspace semantics

An explicit workspace must exist and be an inspectable directory.

Representative outcomes are:

```text
missing path
    -> unavailable

path is not a directory
    -> unavailable

unsafe/uninspectable path
    -> unavailable

valid inspectable workspace
    -> evaluated
```

A valid workspace does not need to contain an Activity merely to be
structurally usable by Concord.

## Exact class semantics

When `class_id` is supplied, Concord inspects exactly that Core class.

It does not:

```text
fuzzy match
substitute another class
select a recent class
create a class
repair a class
```

Representative outcomes are:

```text
valid exact class
    -> ready = True

safely missing exact class
    -> ready = False
    -> notice = concord_class_not_ready

safely detected malformed canonical class/Concord structure
    -> ready = False

unreadable or unsafe requested class state
    -> evaluation = unavailable
    -> ready = None
```

Class metadata remains Core authority.

## Empty Concord state

These are valid:

```text
valid workspace + no class filter + zero Activities
    -> ready = True

valid exact class + zero Activities
    -> ready = True

valid exact class + empty Concord work collection
    -> ready = True
```

Readiness does not require a teacher to have started Concord work.

## Roster boundary

The absence of a roster does not automatically make global Concord readiness
false.

Some later operations require roster-qualified student identity. Those exact
operations continue enforcing their own prerequisites.

Core v1 readiness does not identify which Concord operation the teacher intends
to perform, so #68 does not invent an "all possible workflows are configured"
gate.

## `active_school_year`

`active_school_year` remains neutral request context.

Issue #68 does not add a Concord-specific school-year state machine and does not
make otherwise valid historical work structurally unusable merely because a
different school year is active.

Existing operation-specific Core/Concord rules remain authoritative.

## Stable readiness notices

The bounded public readiness vocabulary is:

```text
concord_readiness_unavailable
concord_class_not_ready
```

`concord_readiness_unavailable` means Concord could not safely evaluate the
supplied context.

`concord_class_not_ready` means the exact requested class context was safely
determined to be missing or structurally unusable.

Notices do not include raw exception text, absolute paths, student identity,
Activity titles, Group identity, record IDs, hashes, routes, JSON, or stack
traces.

## Attention remains separate

Issue #67 attention continues to answer:

> What current Concord-owned work needs teacher attention?

The following may coexist:

```text
readiness.ready = True
attention.summaries = nonempty
```

For example, a valid class may be structurally ready while a GroupPlan awaits
approval.

The following attention categories do not become readiness failures:

```text
Plan
Prepare
Collect
Review
Moderation
Score
Share
```

Readiness does not count attention and does not derive from attention.

## Provider failure isolation

Core owns provider invocation and validation.

Concord therefore preserves these distinct Core outcomes:

```text
module_operations.evaluated
module_operations.evaluation_unavailable
module_operations.provider_failed
module_operations.result_invalid
```

Expected structural inspection failures are converted only where Concord can
state a bounded readiness result safely.

Unexpected programming exceptions are not swallowed by the provider; Core may
report `module_operations.provider_failed`.

Invalid reports remain Core's `module_operations.result_invalid`.

## Read-only guarantee

Readiness evaluation never:

```text
creates or repairs a workspace
creates a class or roster
creates/revises an Activity or Session
creates/revises/applies a GroupPlan
creates Groups or GroupMemberships
instantiates or renders a Packet
allocates PDS2 routes
retains or dispatches scans
assembles evidence
changes Author or Subject state
writes Review or Moderation
creates Scores
registers Academic Work
generates manifests
publishes/supersedes/withdraws
updates recent-context state
```

Focused and installed acceptance compare workspace file fingerprints before and
after readiness evaluation.

## Privacy boundary

Shared readiness output must not contain:

```text
student IDs or names
roster contents
Group or GroupPlan arrangements
grouping-signal values, bands, dimensions or digests
Artifact or scan content
Author or Subject identity
Review notes
Moderation rationale
Scores or Grades
Packet or route IDs
publication IDs
absolute paths
workspace-relative private paths
hashes
raw native records
```

The ordinary shared surface is only:

```text
evaluation
ready
bounded notice code
bounded notice summary
```

## Provider diagnostics / future `pds doctor`

Concord does not implement `pds doctor`.

Core's provider diagnostics already validate the installed:

```text
paper_data_suite.modules
paper_data_suite.publication_producers
paper_data_suite.module_operations
```

profiles independently.

The future Suite doctor may combine:

```text
Core provider diagnostics
+
Concord ModuleReadinessReport
+
Concord ModuleAttentionReport
```

under Suite-owned PASS/WARN/FAIL/SKIP presentation and remediation policy.

Concord does not add a separate "health provider."

## Launcher boundary

The installed teacher application remains:

```text
[project.scripts]
concord = concord.cli:main
```

The module-operations profile is not launcher authority.

The distinctions remain:

```text
installed console application != Core operations provider
launchability != readiness
```

Installed qualification proves the candidate wheel owns the exact console
entry point, resolves outside the source checkout, can print direct help, can
enter the ordinary teacher menu, and can quit cleanly.

The Suite decides whether an exact installed distribution version is
suite-qualified for launch.

## Owner-routed actions

Issue #67 established these opaque Concord-owned actions:

```text
open_activity_plan
open_activity_prepare
open_activity_collect
open_activity_review
open_activity_score
open_activity_share
```

They remain unchanged.

Every shared action uses:

```text
module_id = concord
```

The action ID is not a command, path, URL, callable, or serialized private
context.

A future Suite surface may hand the action back to Concord, but the Suite does
not perform the Concord-owned mutation itself.

## Mixed returned-paper ownership

Unified mixed paper intake is Suite-owned orchestration.

Concord's module-side routing identity remains:

```text
paper_data_suite.modules
    concord = concord.pds_module:get_module_profile
```

Core owns route ownership and dispatch.

Concord's existing handler remains:

```text
handle_concord_route(...)
```

The intended path is:

```text
mixed returned source
    -> Core retained-source custody
    -> Core PDS2 RouteLocator ownership
    -> Core ModuleRegistry / dispatch_routes
    -> owning module handler
    -> owning module state
```

Concord does not create a second mixed-intake queue, batch dispatcher, PDS2
parser, route registry, or retained-scan store.

## Core batch failure isolation

Released Core 0.6.3 `dispatch_routes(...)` processes requests sequentially and
isolates expected per-request failures.

Issue #68 source acceptance proves representative mixed ownership with:

```text
Concord route succeeds
foreign route succeeds

foreign route fails
later Concord route still dispatches

Concord route fails
later foreign route still dispatches

unsupported foreign module
Concord does not claim it as fallback work
```

A malformed or failing Concord-owned route remains Concord-owned failure; it is
never reassigned to another module.

## Concord route authority

`handle_concord_route(...)` remains authoritative for Concord returned pages.

Its existing safeguards remain in force, including:

```text
RouteResolution identity
Concord registration validation
retained-source path agreement
retained-source SHA-256 verification
Artifact Page identity
Activity ownership
route identity
terminal-state rules
deterministic replay
exact source-page provenance
guarded Concord snapshot commit
```

Issue #68 does not replace that handler.

## Replay

The existing Concord handler's deterministic replay behavior is part of mixed
intake qualification.

Replaying the exact same retained source/page against an already recorded
Concord route returns the existing routed result without creating another
Concord mutation.

## Current Suite release boundary

the released Concord v0.2.0 artifact.

That is intentionally separate from this source-level v0.3.0 development work.

Successful #68 implementation means:

```text

for future Suite qualification
```

It does not mean:

```text

```

Issue #68 does not edit the Suite compatibility manifest and does not weaken
exact Suite release qualification.

## Installed-wheel qualification

`scripts/smoke_test_attention_provider_wheel.py` is retained as the historical
filename but now qualifies the complete Core v1 Concord operations profile.

It installs:

```text
exact authenticated pds-core 0.6.3 wheel
candidate pds-concord 0.3.0.dev0 wheel
```

into a fresh virtual environment outside the source checkout.

The smoke removes `PYTHONPATH`, sets `PYTHONNOUSERSITE=1`, runs `pip check`, and
proves sibling/Suite distributions are absent.

It verifies:

```text
routing provider = valid
publication producer = valid
module operations provider = valid

attention_provider = present
readiness_provider = present
```

It then proves:

```text
valid workspace + valid exact class
    -> readiness evaluated, ready=True

valid workspace + safely missing exact class
    -> readiness evaluated, ready=False

missing explicit workspace
    -> readiness evaluation unavailable

draft GroupPlan
    -> readiness remains True
    -> attention is nonempty

workspace fingerprint before readiness/attention
    ==
workspace fingerprint after readiness/attention
```

The same installed environment verifies:

```text
concord = concord.cli:main
```

and exercises installed direct help plus normal teacher-menu start/quit.

## Package boundary

The candidate wheel must contain:

```text
concord/readiness_provider.py
concord/attention_provider.py
concord/pds_operations.py
concord/pds_module.py
concord/pds_publication.py
```

while preserving the existing exact entry points.

The wheel must not contain tests, sibling packages, credentials, source caches,
or a Suite runtime dependency.

## Final architecture

After issue #68:

```text
Paper Data Suite
    |
    +--> future exact release qualification
    +--> future doctor / launcher / mixed-intake orchestration
    |
    v
PDS Core 0.6.3 public contracts
    |
    +--> module operations
    +--> provider diagnostics
    +--> PDS2 routing / dispatch
    +--> retained-source custody
    |
    v
Concord public surfaces
    |
    +--> structural readiness
    +--> teacher attention
    +--> Concord route handler
    +--> concord CLI/menu
    |
    v
Concord-owned domain state
```

Never:

```text
Suite writes Concord-owned domain records
Concord imports Suite orchestration
Concord interprets another module's returned pages
readiness == attention == launchability
```
