# v0.3.1 Teacher-Friendly Routing Review

**Issue:** #109 — Teacher-Friendly Routing Review  
**Release target:** Concord v0.3.1  
**Final qualification baseline:** released `pds-core 0.6.4`  
**Core wheel SHA-256:** `48cea9317f2967bdc0f2d4c14349a56677c7c3f8211f0f33978ccb1a1c75859b`

## Purpose

Issue #109 changes how a teacher chooses an existing Concord route after normal
routing could not safely establish the destination of one retained physical page.

The governing distinction is:

```text
Route scans != Routing Review
```

`Route scans` is normal retain-first PDS2 routing. `Routing Review` is explicit
teacher correction over an already-preserved routing failure.

Routing Review does not guess a route. It does not use OCR, fuzzy matching,
student-name matching, filename matching, AI inference, or "first route"
selection. It does not create or repair route registrations.

The teacher's decision is:

> Which existing Concord Artifact Page does this retained physical page belong to?

The selected teacher-readable row remains bound to one exact existing immutable
Core `RouteLocator`.

## Teacher workflow

Routine Routing Review is:

```text
Routing Review
    ->
choose failed physical page
    ->
review source / physical page / problem / Activity / status
    ->
Route to an existing Concord page
        OR
Defer for later
        OR
Technical details
```

If the failure already carries an exact Concord Class/Activity identity, Concord
skips redundant Class and Activity selection and offers only eligible pages from
that work.

If no trustworthy Activity is known, the teacher chooses:

```text
Class
    ->
Activity
    ->
exact destination page
```

The teacher no longer types Class ID, Work ID, or Route ID in the routine
recovery path.

A known non-Concord route does not offer Concord correction. A failure missing
required retained-page provenance likewise does not offer an impossible normal
route action.

## Failure projection

The open-failure list prioritizes teacher-useful context:

```text
source filename
physical page
problem/category
current status
```

Opaque `failure_id` and route identities remain available through Technical
Details rather than leading routine selection.

Default open review preserves existing semantics:

```text
unresolved -> shown
deferred   -> shown
resolved   -> omitted
```

`Defer` is not dismissal. A deferred failure remains available for later exact
resolution.

## Exact Activity and candidate discovery

Candidate discovery is read-only.

For one selected Activity, Concord loads one exact:

```python
load_activity_read_context(...)
```

and derives route candidates from current `ArtifactPage` and
`ArtifactInstance` state. It does not crawl private Core route directories.

Each routed page produces an exact candidate locator from the current work plus
the page's immutable `route_id`. Concord then authenticates that specific
registration using:

```python
load_route_registration(...)
```

and validates current target eligibility through the shared route authority:

```python
validate_concord_route_target(...)
```

This cross-checks the current Activity, ArtifactInstance, ArtifactPage, page
number, target record, route identity, route status, lifecycle, and immutable
physical fallback where present.

Missing or contradictory registrations are not silently offered as destinations.
Candidate diagnostics distinguish route inconsistency from an Activity that
simply has no eligible pages.

Candidate discovery is read-only and does not create or repair route
registrations.

## Relationship semantics and physical fallback

Teacher-facing labels may show exact current typed context such as:

```text
Session
Group
Packet target
Artifact Author
Artifact Subject
Artifact category
logical page number
physical fallback
```

The semantic boundary is explicit:

```text
Packet target != Artifact Author != Artifact Subject
```

unless current canonical records independently establish the same identity.

`human_fallback` remains immutable physical recovery text. It may be displayed,
but it is never parsed into canonical student, Author, Subject, Group, Session,
or Packet-target identity.

Historical/basic fallback therefore remains useful without becoming a second
relationship model.

## Deterministic selection and identity binding

Candidate ordering is deterministic. Existing menu pagination keeps all
candidates reachable without changing candidate identity.

The selected candidate object carries the exact `RouteLocator`. The route
identity is not reconstructed from teacher-facing display strings after
selection.

Browsing, Class selection, Activity selection, candidate selection, pagination,
Technical Details, Back, Main Menu, Quit, and canceled confirmation are
zero-write operations.

## Confirmation and mutation authority

Defer uses an editable default note and requires literal:

```text
DEFER
```

Route correction uses an editable default note and requires literal:

```text
RESOLVE
```

Only after `RESOLVE` does the teacher workflow delegate to the existing direct
mutation authority:

```python
resolve_routing_failure_with_route(...)
```

The service remains usable independently of menu state.

That service preserves the original routing-failure identity, retained scan
identity, source SHA-256, retained path, physical page number, exact immutable
route registration, Core module dispatch, and append-only resolution metadata.

## Stale-state protection

Menu state is not trusted as mutation authority.

Immediately before dispatch, the service re-reads current append-only resolution
state. If another action already resolved the failure, it raises:

```text
RoutingFailureAlreadyResolvedError
```

and performs no second dispatch or misleading later resolution write.

A deferred failure remains eligible for a later real resolution.

The final route handler also reloads current Concord state. If a destination
became invalid after the teacher selected it, dispatch fails closed rather than
substituting another route.

## Retained-source and replay boundaries

Routing Review does not bypass retained-source validation.

The retained source must continue to satisfy the existing exact checks for:

```text
workspace containment
Core-canonical retained filename
SHA-256 identity
source scan identity
physical page identity
```

The Concord route handler independently verifies retained bytes before filing
evidence.

If the exact retained scan/page/route occurrence already exists, existing
`ScanReference` replay semantics remain idempotent. Routing Review does not create
a duplicate returned-evidence occurrence merely because the teacher reviews the
same exact physical page again.

## Route-registration immutability

Routing Review selects only existing immutable routes.

It does not call route-registration creation or reconciliation as part of
candidate browsing or correction. Successful resolution leaves the selected Core
route registration byte-for-byte unchanged and creates no new route.

PDS2 payloads, existing route IDs, and historical physical pages remain unchanged.

## Compatibility and migration

Issue #109 requires no workspace migration.

It does not migrate or reinterpret existing:

```text
Core classes
Activities
ArtifactInstances
ArtifactPages
PacketInstances
RouteRegistrations
PDS2 payloads
retained scans
RoutingFailureMetadata
ScanResolutionMetadata
ScanReferences
returned student evidence
```

The declared runtime dependency remains:

```text
pds-core>=0.6.3,<0.7
```

Final qualification uses Core 0.6.4 because it is the current released
qualification baseline; that does not raise the declared dependency floor.

Dedicated installed acceptance is:

```text

```

The harness authenticates the exact released Core 0.6.4 wheel using SHA-256:

```text

```

It creates an isolated virtual environment, installs the candidate Concord wheel
and exact Core wheel, runs `pip check`, verifies both imports originate in
`site-packages`, and executes the synthetic scenario under:

```text

```

The installed scenario proves:

```text

known Concord work -> Class/Activity selection is skipped
exact candidate RouteLocator remains bound to the teacher row
existing Core registration is authenticated

ScanReference filing succeeds
resolution metadata records the same exact route

stale terminal state blocks redispatch
```

The authoritative repository validator invokes this smoke against the exact
candidate wheel it just built.

## Non-goals

Issue #109 does not change PDS2, normal #103 Scan Routing, returned-evidence
opening, Artifact Review, scoring, publication, grading, route storage, or Core
route enumeration.

It adds no OCR, AI routing, fuzzy matching, automatic student matching, persistent
candidate cache, generic filesystem browser, route repair, route migration, or
new Core API.

The feature changes how the teacher chooses an exact existing route, not what
that route means.
