# Concord v0.3.0 Starter Collaborative-Learning Template Library

**Issue:** #61  
**Status:** Implemented on the v0.3.0 development line

## Purpose

Issue #61 ships a substantial synthetic starter library so Concord can be useful
for common high-school collaborative-learning workflows without requiring every
teacher to author reusable Templates from scratch.

The starter catalog is deliberately a **package-owned source catalog**, not a
second canonical Template authority:

```text
installed Concord package
    -> immutable starter catalog metadata/assets
    -> explicit teacher installation
    -> #58 Template workflow/storage authority
    -> shared/concord/templates/<template_id>/
```

Browsing the catalog is read-only. Importing Concord, opening a workspace,
listing Templates, or opening the Template Library does not install anything.
Installation is an explicit teacher action.

After installation a starter is an ordinary reusable `TemplateDefinition` /
`TemplateVersion` lineage. The packaged source has no privilege over canonical
teacher state: teachers can revise metadata, create immutable successor Versions,
activate successors, or retire the lineage through the existing #58 workflows.

## Shared paper design

The starter library uses a common paper-first design system:

- US Letter;
- monochrome / grayscale;
- high contrast;
- ordinary copier/printer friendly;
- generous handwriting areas;
- compact directions;
- strong section labels;
- no semantic dependence on color;
- portrait by default;
- landscape only where horizontal working space is materially useful.

The starter specifications reserve reusable rendering inputs such as Activity
title, Session label, Group label, participant display label, date, teacher
prompt/topic, criterion label, and future route/fallback slots where appropriate.
They do not persist concrete Activity, Session, Group, student, criterion, or
route identities.

## `concord_starter_layout_v1`

Issue #58 intentionally stores exact rendering-specification bytes without
interpreting them. Issue #61 therefore defines the smallest bounded layout
contract needed to describe the starter forms:

```text
concord_starter_layout_v1
```

The contract is strict, canonical JSON. It is declarative and non-executable.
It describes paper orientation, page titles/instructions, simple headings,
response boxes, tables, selection areas, drawing/annotation areas, and the
semantic response-region keys that correspond to the reusable Template
contract.

It does **not** contain Python, shell, JavaScript, arbitrary expressions,
unrestricted object traversal, or executable template code.

Each package-owned layout asset has exact immutable bytes and a SHA-256 digest.
Each starter `TemplateVersion` binds the asset through its exact rendering
reference and digest. Page count, page order, response regions, rendering inputs,
return behavior, privacy, authorship/Subject expectations, and compatibility are
validated against the reusable #57 Template contracts.

Actual Activity-specific layout binding, Artifact/Page creation, PDF generation,
and Core PDS2 route allocation remain #62.

## Stable identities

Starter keys, Template IDs, initial Template Version IDs, and rendering references
are deterministic across installations.

Examples:

```text
think_pair_share
starter-think-pair-share
starter-think-pair-share-v1
starter-think-pair-share-layout-v1
```

Installing a starter never generates a random reusable identity.

The initial packaged Version is installed `active`/current because the shipped
starter is a ready-to-use default. Teacher customization uses an ordinary
successor Version rather than mutating that immutable initial Version.

## Installation states

For each packaged starter Concord reports one of:

```text
missing
already_installed
conflict
```

`missing` means the canonical Template identity is absent.

`already_installed` means the exact packaged initial Template Version remains in
the canonical lineage. Later teacher metadata revisions, successor Versions, or
retirement do not make the package owner of that lineage again. Reinstall is an
exact no-op and never resets teacher state or silently reopens a retired
Template.

`conflict` means the stable packaged Template identity exists but does not
contain the compatible packaged initial Version semantics. Concord fails
explicitly rather than overwriting the lineage.

## Install one

The noninteractive flow is:

```text
concord template starter-list
concord template starter-show --starter-key <key>

concord template starter-install \
    --starter-key <key> \
    --actor-id <actor>
```

`starter-list` and `starter-show` are read-only and do not initialize an absent
workspace.

`starter-install` prepares the exact packaged source, records imported
provenance for the explicit actor, revalidates packaged metadata and rendering
bytes, and commits through `create_template_library`, the same canonical #58
storage authority used by ordinary Template creation.

## Install all missing

Use:

```text
concord template starter-install-all --actor-id <actor>
```

The prepare phase examines all 30 starters before writing. An incompatible
identity aborts preflight before any new starter is installed.

The commit phase runs in deterministic catalog order. Existing exact starters are
reported as `already_installed`; only missing starters are created. Replaying the
operation is idempotent.

Each Template library is independently atomic under #58. A multi-Template
install cannot make 30 independent Template libraries one filesystem
transaction, so a later failure after earlier successful creates is reported as
`StarterTemplateInstallAllPartialSuccessError`. The result identifies completed
starters and the failed starter; rerunning is safe because exact earlier installs
are idempotent.

## Teacher menu

The workspace-level `Template Library` includes:

```text
9. Browse / install starter Templates
```

The nested Starter Template Library provides:

1. Browse / preview starter Templates
2. Install one starter Template
3. Install all missing starter Templates

Browsing is read-only. Writes require the literal confirmation word:

```text
INSTALL
```

H/B/M/Q navigation remains consistent with the rest of Concord.

## Privacy, authorship, and subjects

Starter state contains identity-free reusable defaults only.

Typical group working forms use `group_and_teacher`. Individual peer-review or
reflection forms may use `teacher_and_subjects`. The Team Health / Contribution
Check defaults to `teacher_restricted`.

These are reusable policy expectations, not concrete access-control membership.
#62 resolves effective instance privacy and must not silently broaden a more
restrictive policy.

Likewise, starter Templates may declare reusable authorship expectations such as
`individual_author`, `recorder_for_group`, or `collective_group_author`, and
reusable Subject expectations such as `core_student`, `concord_group`,
`concord_session`, or `concord_activity`. Issue #61 creates no actual
`ArtifactAuthor` or `ArtifactSubject` records.

## Authority boundaries

The starter catalog is convenience content only. Preserve these distinctions:

```text
starter Template != Activity
starter Template != GroupPlan
starter Template != Group
starter role suggestion != canonical Role
student project plan sheet != Concord GroupPlan
peer review form != ArtifactReview
peer review form != Score
CER form != scientific correctness judgment
reflection selection != OMR
Template response region != EvidenceReference
Template subject expectation != ArtifactSubject
Template authorship expectation != ArtifactAuthor
Template route slot != RouteRegistration
Template Version != ArtifactInstance
Template page definition != ArtifactPage
```

In particular, Group Roles & Responsibilities prints generic classroom role
suggestions but does not create #64 reusable Role/Responsibility preset authority.

## Deliberate exclusions

Issue #61 does not implement:

- Activity-specific Template instantiation;
- Packet Instance creation;
- Artifact Instance or Artifact Page creation;
- Core PDS2 route allocation;
- QR/PDS2 binding;
- PDF generation or printing;
- scanning, OCR, OMR, or handwriting recognition;
- Group/GroupMembership/GroupPlan writes;
- grouping-signal use;
- RoleAssignment creation;
- ArtifactAuthor or ArtifactSubject creation;
- Review/Moderation records;
- Criteria, Scales, or Scores;
- Publication;
- automatic peer grading;
- general-purpose document editing.

Those remain with #62 or their existing/future authorities.

## Package and release qualification

`pyproject.toml` includes the starter JSON assets as package data.

Repository qualification checks this at two levels:

1. `scripts/check_package.py` requires the starter Python modules and the exact
   30 JSON rendering assets in the built wheel.
2. `scripts/smoke_test_wheel.py` imports the catalog from an isolated installed
   wheel, loads all 30 package resources, verifies their strict layouts/digests,
   and confirms no source-checkout fallback is required.

This prevents a checkout-only success where starter metadata exists in source
but the rendering assets are omitted from the release artifact.
