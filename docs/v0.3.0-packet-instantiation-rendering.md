# v0.3.0 Activity-specific Packet instantiation and PDS2 rendering

**Status:** Implemented in issue #62.

Issue #62 is the first complete Concord path from a reusable Packet Version to
Activity-specific printable paper. It resolves exact reusable Packet and Template
history against one canonical Activity/Session context, expands bounded audience
semantics, creates fresh runtime identities only after review, reconciles immutable
Core PDS2 routes, and renders deterministic PDFs.

The authority chain is:

```text
Packet Definition
  -> exact Packet Version
    -> exact Template Version(s)
      -> Activity + explicit Session
        -> concrete Packet target(s)
          -> PacketInstance
            -> ArtifactInstance
              -> ArtifactPage
                -> Core PDS2 route
                  -> deterministic PDF
```

A reusable Packet Version is never itself an Activity-specific PacketInstance.

## Runtime records and provenance

Issue #62 adds the Activity-owned runtime contracts:

```text
PacketInstance
PacketInstanceArtifactBinding
PacketTargetContext
PacketRenderingValue
```

`PacketInstance` records one concrete target for one exact Packet Version. One
teacher generation request may create several Packet Instances and therefore also
carries a durable `generation_id`.

The runtime record preserves exact reusable provenance without copying reusable
bodies into Activity-native state:

```text
packet_definition_id
packet_version_id
packet_component_id
template_id
template_version_id
generation_id
packet_instance_id
artifact_instance_id
artifact_page_id
```

`PacketInstanceArtifactBinding` also freezes component sequence and `copy_index`.
The same Template may therefore appear several times without relying on display
labels or page order to reconstruct provenance.

The generated runtime models deliberately contain no GroupPlan strategy, seed,
grouping-signal set, grouping-signal dimension, signal band, or proficiency
field.

## Zero-write preparation

`prepare_packet_instantiation(...)` is the zero-write planning boundary.

Preparation resolves:

- the Core class and roster;
- the canonical Activity;
- one explicit Session;
- the exact Packet Definition and exact Packet Version;
- every exact referenced Concord Template Definition/Version;
- verified rendering-specification bytes and SHA-256;
- component requirement/condition semantics;
- canonical Groups, Memberships, RoleAssignments, participants, Activity, and
  teacher targets as applicable;
- copy counts;
- teacher-controlled rendering bindings;
- privacy, proposed authorship, and proposed Subject associations;
- exact Packet Instance, Artifact, Page, and route counts; and
- deterministic target/component/copy/page order.

Preparation allocates no PacketInstance, ArtifactInstance, ArtifactPage, route,
or PDF identity. It returns a `review_digest` bound to the relevant canonical
state and rendering assets.

The preview exposes skipped or blocked components and the reason. An unresolved
required rendering input, unsupported rendering contract, unusable Activity or
Session, stale roster/context, or `external_component` aborts before mutation.

`external_component` remains structurally valid reusable Packet state from #59,
but issue #62 does not import sibling runtimes or invent a sibling resolver.

## Component and target semantics

`copies_per_target` expands into distinct Artifact and Page identities. Copies
never share Core route IDs.

Requirement levels remain bounded:

- `required` is included whenever applicable;
- `recommended` is included by default and may be explicitly omitted;
- `conditional` uses only the declared bounded condition;
- `teacher_choice` requires an explicit yes/no decision;
- `matching_role_present` consults canonical RoleAssignments;
- `group_context_present` requires an applicable Group context; and
- `participant_context_present` requires an applicable participant context.

Group targets consume ordinary canonical `Group` records. A Group created by an
applied GroupPlan is indistinguishable from another canonical Group for Packet
generation. The generator never follows a Group back to a GroupPlan.

Participant identity comes from Core roster authority. Role targets use canonical
RoleAssignments and exact Effective Context. Teacher targets use the explicit
workflow actor. Activity targets use the selected canonical Activity.

## Rendering input authority

System-controlled inputs are resolved by Concord and cannot be overridden by a
teacher binding:

```text
activity_title
session_label
group_label
participant_display_label
current_date
pds2_route_payload
human_fallback
```

The generation date is frozen for retry. PDS2 payload and human fallback are
derived only after the immutable Core route identity exists.

Teacher-controlled rendering values such as `teacher_text` and
`criterion_label` are structured, type-checked, length-checked, included in the
review digest, and frozen into the exact generated Artifact binding.

The exact Template rendering asset is loaded from canonical Template history and
verified against `rendering_specification_sha256`. Issue #62 renders the strict,
non-executable `concord_starter_layout_v1` contract shipped by #61; arbitrary
rendering code is not executed.

## Privacy, authorship, and Subjects

Packet audience intent is not authorization. Instance privacy begins with the
exact Template Version default and may only become more restrictive. Failure to
resolve a required concrete audience fails closed or uses `teacher_restricted`
only when that fallback is semantically valid.

The following remain distinct:

```text
audience != author
membership != author
role assignment != author
subject != author
route target != author
```

Generation may create only semantically justified proposed ArtifactAuthor and
ArtifactSubject associations. Generation alone never confirms that a student
actually authored, contributed to, or was the Subject of returned work.

GroupPlan and grouping-signal details are a hard privacy boundary. Generated
Packet records, route-registration `module_details`, PDS2 payloads, PDFs, and
ordinary CLI/menu output do not carry planning strategy, seeds, signal-set IDs,
signal dimensions, signal bands, or proficiency-like values.

Core route metadata is intentionally minimal:

```text
activity_id
artifact_instance_id
artifact_page_id
page_number
```

Every route targets:

```text
module_id = concord
record_kind = artifact_page
```

## Commit, route reconciliation, rendering, and retry

`commit_packet_instantiation(...)` revalidates the exact reviewed state before
allocating identities. It creates the native generation graph in one Activity
snapshot where feasible, reconciles immutable Core routes, then advances the
runtime lifecycle toward rendering.

Cross-authority recovery never deletes a valid Core route to simulate rollback.
Typed partial-success states retain the durable generation identity and tell the
caller which stage requires reconciliation.

`resume_packet_instantiation(...)` reuses the same `generation_id`,
PacketInstance IDs, Artifact IDs, ArtifactPage IDs, and route IDs.

`render_packet_generation(...)` renders every target-specific Packet Instance in
one generation. `render_packet_instance(...)` renders one Packet Instance and,
for an already completed Packet, performs an exact reprint. A reprint verifies
the deterministic output and reuses the existing routes rather than allocating
new ones.

Successful output is installed under the Activity work tree as:

```text
rendered/packets/<packet_instance_id>.pdf
```

The Packet Instance retains the relative output path and SHA-256 only after the
output is durable and verified.

## Direct CLI

The fully noninteractive runtime Packet commands are:

```text
concord packet instantiate-preview
concord packet instantiate
concord packet instantiate-resume
concord packet instance-list
concord packet instance-show
concord packet instance-render
concord packet generation-render
```

`instantiate-preview` performs no writes and prints the `review_digest`.
`instantiate` requires that exact digest. An optional caller-supplied
`--generation-id` supports deliberate retry/reconciliation without duplication.

An optional `--options-file` is a strict JSON object containing only:

```json
{
  "component_choices": [],
  "rendering_bindings": []
}
```

There is no force, latest-Template substitution, skip-preview, or route-ID input
mode.

## Teacher menu

An opened Activity now exposes:

```text
Prepare / Generate Packet
```

The teacher chooses an active reusable Packet, selects the Session, resolves
required teacher choices/bindings, reviews exact target/artifact/page/route
counts and diagnostics, and must type:

```text
GENERATE
```

before native generation is committed.

The same submenu lists and inspects Packet Instances, renders or reprints an
exact instance, and resumes incomplete route reconciliation. Teachers never need
to enter Artifact Page IDs, route IDs, QR payloads, or placeholder Template IDs
for the normal path.

## Starter visual-review gate

The issue #61 starter catalog was exercised through the actual #62 Packet-backed
generation/rendering path using synthetic-only Activity, Session, Group,
participant, and teacher data.

The accepted final visual-review run produced:

```text
30 starter Templates
35 rendered physical pages
35 mechanically decoded PDS2 QR codes
ZIP SHA-256:
26146b994a273a0ab377846494f5498bf2f16017e6c95b779540d976722874e9
```

Human review identified and corrected two renderer defects before approval:

- Venn Comparison needed a materially larger writable overlap; and
- Concept Map / Connection Web connectors needed to terminate at shape
  boundaries rather than crossing node interiors.

The regenerated review bundle passed the mechanical QR gate and the corrected
forms were visually accepted. Visual review is therefore part of #62 acceptance,
not merely an automated-test artifact.

## Installed-wheel and repository qualification

`scripts/smoke_test_wheel.py` includes an isolated installed-distribution Packet
generation smoke against the released Core 0.6.3 baseline. It creates synthetic
class/Activity/Group state, installs one packaged starter through canonical
Template storage, creates an exact reusable Packet, performs zero-write prepare,
commits native generation and Core routes, renders the Packet PDF, and verifies
runtime inspection/reprint identities.

The full repository gate remains:

```text
python scripts/validate_repository.py --core-wheel <pds-core-0.6.3 wheel>
```

That gate covers pytest, Ruff, strict Mypy, documentation checks, compatibility,
build/Twine/package inspection, release-artifact verification, isolated wheel
smoke, installed producer acceptance, and `git diff --check`.

## Handoffs

Issue #62 owns generation and physical rendering, not Activity copying or preset
authoring.

Issue #63 may copy Activities while preserving the reusable/instance boundary; it
must not clone old PacketInstance, ArtifactPage, or Core route identities as a
new generation.

Issue #64 may add reusable Role, Responsibility, Criterion, and Scoring Scale
presets. Those reusable helpers do not change the #62 runtime Packet provenance,
privacy, or retry contract.

## Issue #65 guided-workflow integration

The guided **Classroom Materials** step selects a saved Packet and then enters
the existing zero-write Packet preview / explicit `GENERATE` flow. A standalone
saved Template is first committed as an ordinary reusable one-part Packet; no
direct Template-to-Artifact or alternate PDS2 path was introduced.
