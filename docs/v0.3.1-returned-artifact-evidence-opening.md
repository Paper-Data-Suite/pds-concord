# v0.3.1 Returned Artifact Evidence Opening

**Status:** Implemented for issue #105.

Issue #105 adds a read-only teacher boundary for opening the exact existing PDF
assembly of returned Artifact evidence in the operating system's default PDF
application. The feature composes Concord's existing returned-evidence lineage,
assembly-integrity, and teacher task authorities instead of creating a second
evidence model.

## Authority

The authoritative evidence chain remains:

```text
physical returned paper
-> Core retained source scan
-> Concord ScanReference
-> ArtifactPage return state
-> exact returned-page lineage
-> verified returned-Artifact assembly PDF
```

The presentation-independent boundary is:

```text
resolve_returned_artifact_assembly(...)
    ->
open_returned_artifact_evidence(...)
```

`resolve_returned_artifact_assembly` derives the exact assembly identity from the
current canonical Artifact/ArtifactPage/ScanReference lineage, verifies retained
source custody, verifies the existing immutable assembly manifest and PDF digest,
and returns `ResolvedReturnedArtifactAssembly`. It never creates or repairs an
assembly.

## OPEN != ASSEMBLE

Open requires an already-existing exact assembly. If the selected evidence has
not been assembled, the teacher is directed to **Assemble returned work** first.

Open does not:

```text
assemble pages
render a replacement derivative
repair a missing or tampered assembly
choose a different duplicate returned occurrence
search for a plausible PDF
create cache/temp copies
persist opened/viewed history
```

`assemble_returned_artifact(...)` remains the sole assembly authority.

## OPEN != REVIEW

Opening evidence is not an Artifact Review. It does not create, replace, revise,
or imply a Review or Moderation judgment. Review remains an explicit human
evidence-readiness decision after the teacher has inspected the work.

## OPEN != SCORE

Opening evidence does not create, revise, infer, or imply a Score, Score Evidence
Link, grading judgment, or downstream publication state.

## Exact duplicate-occurrence selection

When more than one valid returned physical occurrence exists for an Artifact
Page, Concord does not choose latest, first, newest, or any other implicit
candidate. The existing teacher occurrence-selection UI supplies exact
`AssemblyPageSelection` values. Those selections derive the deterministic exact
assembly identity. An assembly for a different occurrence is never substituted.

## Currentness and concurrency

The teacher task UI loads the current Activity snapshot before Artifact and
occurrence selection. That `expected_snapshot_revision` is passed into the
resolver. If canonical state changed after teacher selection but before
resolution, Open fails closed and asks the teacher to retry.

After retained-source and assembly verification, the resolver rereads the
canonical current pointer and requires both:

```text
current.snapshot_revision == selected snapshot revision
current.snapshot_sha256 == selected snapshot SHA-256
```

A changed revision or `snapshot_sha256` fails before the local viewer boundary.
Open remains read-only; there is no write token or lock held across the operating
system viewer launch.

## Assembly integrity and path safety

The exact assembly is the derived path under:

```text
attachments/artifacts/<artifact_instance_id>/assemblies/<assembly_id>/
    artifact.pdf
    manifest.json
```

The existing assembly authority rejects incomplete output, manifest/PDF digest
mismatch, contradictory lineage, path substitution, work-root escape, and
symlink or Windows link-like/reparse redirection where supported by the host.
Open never accepts an arbitrary teacher-entered path.

## Teacher workflow

Routine Collect, Review, and Score screens expose the same local action:

```text
O. Open returned work
```

Collect keeps its numbered actions unchanged:

```text
1. View returned work
2. Assemble returned work
3. Confirm who produced the work
4. Confirm who or what the work is about
O. Open returned work
```

Review and Score expose the same `O` action without entering Review, Moderation,
Score recording, or Score revision workflows merely because evidence was opened.

A successful launch reports:

```text
Returned work opened in your default PDF viewer.
```

Routine teacher failures use controlled privacy-minimal messages. Raw retained
paths, complete ScanReference metadata, assembly hashes, manifest JSON, and
internal route payloads are not printed.

## Collection-state semantics

The existing collection authority remains the teacher-facing readiness model:

```text
not_applicable
not_ready
ready
selection_required
assembled
needs_recovery
```

These mean, respectively: there is no return-expected evidence; required evidence
is incomplete; exact evidence is complete but has no assembly; duplicate returned
occurrences require teacher selection; the exact assembly exists and verifies;
or an expected assembly exists but fails integrity verification.

Open preserves these distinctions. In particular, it does not turn `ready` into
`assembled`, `not_ready` into a partial open, or `needs_recovery` into implicit
repair.

## Core local-open boundary

Only after exact resolution, integrity verification, and final currentness
verification does Concord delegate to:

```python
pds_core.local_open.open_local_path(...)
```

A Core `LocalOpenError` becomes `ConcordWorkflowOpenError`. Viewer-launch failure
is therefore distinct from evidence-integrity failure.

## Direct CLI boundary

Issue #105 adds no new direct CLI command. The public presentation-independent
workflow services are available to Concord callers, while the routine user
surface is the task-oriented teacher menu. This avoids adding an arbitrary-path
or identifier-heavy teacher command merely to mirror a local UI action.

## Historical compatibility

Existing returned Artifact assemblies remain valid only when their exact stored
manifest/PDF and current source lineage verify. Open does not rewrite old
assemblies or reinterpret them using package-current semantics. No workspace
migration or new canonical record type is introduced.

## Issue #105 installed-wheel acceptance

`scripts/smoke_test_returned_artifact_evidence_opening_wheel.py` is the
authoritative isolated-wheel gate. It installs the candidate Concord wheel with
the exact released Core 0.6.3 qualification wheel and runs the acceptance program
under `python -I`.

The installed-only scenario proves:

```text
isolated site-packages provenance
fresh Core/Concord workspace
real Artifact Page and PDS2 route
real retained returned image and ScanReference
real exact returned-Artifact assembly
exact resolver path/digest identity
fake local opener receives only the verified PDF
canonical snapshot revision/SHA and graph are unchanged by Open
no Review, Moderation, or Score is created
stale teacher selection is rejected before viewer launch
tampered PDF is rejected without repair
missing manifest is rejected without regeneration
LocalOpenError is translated after successful evidence verification
```

The smoke is wired into `scripts/validate_repository.py` as:

```text
installed-wheel smoke: issue #105 returned Artifact evidence opening
```

so final repository qualification carries the same installed boundary.

## Non-goals retained

Issue #105 does not add an embedded viewer, thumbnails, OCR/AI interpretation,
arbitrary filesystem browsing, implicit assembly or repair, view history,
automatic Review/Moderation/Score judgments, distribution packaging, or a new
storage/cache layer.
