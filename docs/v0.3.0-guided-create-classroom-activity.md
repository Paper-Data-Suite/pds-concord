# Guided Create Classroom Activity workflow

**Status:** Implemented for Concord v0.3.0 issue #65  
**Compatibility:** Python 3.11+; `pds-core>=0.6.3,<0.7`

## Purpose

Issue #65 adds a teacher-facing **Create Classroom Activity** and **Continue
setup for an Activity** workflow over Concord's existing exact services. The
guide does not define a second Activity model, a wizard database, or alternate
Packet/scoring/grouping paths. It translates classroom decisions into the
already-qualified Concord workflows introduced through issues #48-#64.

The normal teacher path is intentionally expressed in classroom language:

```text
choose class
    -> choose a fresh or copied starting point
    -> create Activity + first Session
    -> choose classroom materials
    -> decide how students will work
    -> assign Roles / Responsibilities as useful
    -> set up assessment when the Activity is scored
    -> review current setup
    -> prepare materials now or finish for now
```

The exact direct CLI remains noninteractive and unchanged for automation,
recovery, diagnostics, and expert use.

## Recoverable, incremental setup

The guide is deliberately **not** an all-or-nothing wizard transaction. Existing
Concord operations have their own valid write and approval boundaries. Once a
teacher confirms one of those operations, that canonical state remains valid
when the teacher backs out of a later step, chooses **Finish for now**, or closes
Concord.

No persistent `WizardState`, checklist record, or shadow setup authority is
created. **Continue setup** derives the current picture from canonical state by
calling `inspect_guided_activity_setup`.

The derived setup areas are:

- Activity basics;
- Session;
- Classroom materials;
- Student groups;
- Roles and responsibilities; and
- Assessment.

Derived statuses use teacher-facing terms such as **Ready**, **Needs attention**,
**Not set up**, and **Not used**. They are read-only interpretations, not stored
records.

This means Activity state created through advanced menus or direct CLI is
recognized by the guide automatically. There is no separate wizard completion
flag that can drift from the Activity graph.

## Fresh Activity creation

The guided fresh path asks for the class and classroom-facing Activity details,
then generates native Activity and Session identifiers internally. Teachers are
not asked to invent IDs.

The guide maps teacher-facing labels onto the existing supported Activity types
and scoring orientations. For example, `socratic_seminar` is shown as
**Discussion / seminar**, and `standards_based` is shown as **Standards-based
assessment**.

Activity + first Session creation continues to use the existing atomic
`create_activity_context` workflow. The review shown before the teacher types
`CREATE` is zero-write. Canceling before that confirmation creates no Activity.

Standards-based and mixed Activities continue to resolve their standards profile
and Focus Standards through Core. The guide does not copy or remap standards
heuristically.

## Starting from another Activity

The guided copy path composes issue #63's `prepare_activity_copy` and
`copy_activity` services. It preserves the #48/#63 rule:

> copy Activity configuration != clone Activity state

The preview remains zero-write and the target receives fresh native identities.
The guide does not copy prior Groups, assignments, evidence, returned scans,
review/moderation history, Scores, publications, or other operational history
excluded by #63's positive allowlist.

The teacher-facing review explains what is carried forward and what is not
without exposing source snapshot digests or internal provenance structures.

## Classroom materials

The guided materials screen offers four normal choices:

```text
Use a saved Packet
Start with a saved Template
Manage saved materials
Decide later
```

### Saved Packet

A selected active Packet is handed to the existing Packet generation service.
The guide does not duplicate issue #62 generation logic. The existing operation
still resolves one explicit Session, prepares concrete targets, performs a
zero-write preview, and requires explicit `GENERATE` confirmation before fresh
PacketInstance / Artifact / ArtifactPage / Core PDS2 routing state is written.

### Saved Template

A standalone Template is not rendered directly to classroom Artifacts. The
guide first prepares a normal reusable one-part Packet referencing the exact
immutable Template Version through `prepare_packet_from_template`.

That preparation is zero-write. After review, `commit_packet_from_template`
creates an ordinary active Packet through canonical Packet storage. Exact
Template-version dependencies are revalidated by normal Packet storage on
commit. Only then may the teacher enter the ordinary Packet generation path.

Therefore the runtime paper authority remains:

```text
Template Version
    -> Packet Version
    -> Activity-specific Packet preparation
    -> Artifact / ArtifactPage
    -> Core PDS2 route
```

There is no Template-to-Artifact shortcut and no hidden Activity field storing a
"selected Packet" that has not been prepared.

## Student groups and GroupPlans

The guide asks **How will students work?** and routes to existing direct Group or
GroupPlan services. It does not collapse planning and canonical classroom state.

```text
GroupPlan != Group != GroupMembership
```

An unfinished GroupPlan is derived as **Needs attention**. An approved GroupPlan
is described as ready to apply, but the guide never treats navigation as teacher
approval. Existing explicit GroupPlan review/application boundaries remain
mandatory.

Grouping signals remain temporary teacher-restricted planning inputs. Signal
values are not copied into guided Activity summaries, materials summaries,
Artifacts, routes, result manifests, publications, or other unrelated output.
Meridian remains optional; signal-informed planning continues to use Core's
neutral interchange.

## Roles and Responsibilities

The guide presents Roles and Responsibilities as classroom decisions such as
**Who has which role?** and **What does each person need to do?** It routes to the
existing manual and reusable-preset operations.

Applying a preset continues to materialize fresh Activity-native assignment
state. Preset lineage/revision mechanics are not required for routine teacher
interaction, and prior assignment/student/history state is never reused merely
because a reusable definition was selected.

## Assessment

The guide asks **How will you assess this activity?** rather than presenting the
internal `scoring_orientation` key as the main teacher language.

Evidence-only Activities derive assessment as **Not used** and create no Scores.
Scored Activities route into the existing Criterion Set / Scoring Scale setup,
including issue #64 reusable presets. Standards-backed Criterion Sets continue
to revalidate through Core against the target Activity context.

Setup creates **zero Scores**. A Score remains later professional judgment over
actual evidence; it is not reusable configuration and is not implied by
Activity setup.

## Review and preparation

**Review Classroom Setup** is a derived status screen, not a second aggregate
commit. It summarizes current canonical setup and lets the teacher:

- prepare materials now;
- change a setup area; or
- finish for now.

Already-confirmed work is neither recommitted nor rolled back. Material
preparation retains its own zero-write preview and explicit confirmation.

## Information Density and screen-refresh contract

Issue #65 makes the Paper Data Suite Information Density policy explicit for the
Concord teacher interface:

> Clearing/redrawing the screen is the default. Information remains visible only
> when the teacher needs it to complete the current action.

The guided workflow therefore uses a focused-screen model:

1. clear/redraw when moving to a new decision, review, result, help view, or
   corrective action;
2. show a short orientation header;
3. retain only the context needed for the current decision;
4. show the current choices or prompt;
5. avoid leaving prior prompts, long validation transcripts, or completed-step
   output above the new action.

Examples of useful retained context are the Activity title, class context where
needed, and the current setup area. Routine screens avoid raw UUIDs, storage
paths, revision hashes, review digests, provenance objects, raw JSON, provider
keys, and grouping-signal details.

Long selections continue to use the shared bounded selection/paging helpers.
Routine errors redraw the current decision with a concise explanation and a
useful next action rather than building a scrolling history of failed attempts.

This contract is intended to carry forward into issue #66's task-oriented menus
and issue #67's attention summaries.

## Back, cancel, stale state, and interruption

The guide follows the durable Concord rule:

```text
before confirmation -> cancel means no write
after confirmation  -> valid canonical state remains
```

Back or **Finish for now** does not attempt compensating deletion. Reopening
Concord and choosing **Continue setup** reconstructs the current picture from
canonical records.

Existing snapshot/review-digest protections continue to guard operations that
have zero-write previews. If state becomes stale, the operation must be prepared
again from current canonical state rather than silently committing an outdated
preview.

## Advanced and direct interfaces

Issue #65 does not remove exact operations. Activity Management exposes the
normal guided path first and keeps **Advanced Activity tools** available.
Opened Activities also expose **Continue Classroom Setup**.

The direct CLI remains deterministic and noninteractive. Scripts should continue
to use exact commands such as `concord activity create`, `concord activity
copy-preview`, `concord group-plan apply`, `concord role-preset`, `concord packet
instantiate-preview`, and the existing scoring commands rather than attempting
to automate the interactive teacher guide.

## Privacy and authority boundaries

The guide preserves the implemented v0.3.0 authorities:

- Core owns workspace, class/roster, standards, and PDS2 infrastructure;
- Concord owns its Activity, Session, Group, assignment, Artifact, review,
  scoring, reusable Template/Packet, and preset domains;
- GroupPlan remains planning rather than canonical membership;
- reusable definitions remain distinct from Activity-native materialized state;
- Score != reusable configuration;
- existing Activity evidence/history is not copied into new Activities; and
- no Meridian runtime dependency is introduced.

The guide is presentation/orchestration over those services, not a simplified
second implementation of them.

## Qualification

Issue #65 qualification includes:

- focused guided-workflow tests;
- explicit screen-refresh / Information Density checks;
- safe fresh and copied creation tests;
- canonical-state-derived resume tests;
- GroupPlan attention-state tests;
- teacher-readable enum-label checks;

- wheel package inclusion checks for the guide/service modules; and
- `scripts/smoke_test_guided_activity_wheel.py` against released Core 0.6.3.

The installed-wheel smoke proves that an installed Concord distribution can
create a fresh Activity, derive partial setup, preserve it across a second
inspection, recognize canonical Group/assignment changes created through normal
services, and import the teacher guide without source-tree dependencies.

Deep installed Packet-generation and reusable-preset mechanics remain qualified
by their existing #62 and #64 installed smokes, which the repository validator
continues to run alongside the #65 smoke.

Milestone-wide representative physical print/scan acceptance remains issue #70.


## Handoff to task-oriented opened Activity navigation

Issue #66 builds directly on this guide without replacing it. **Continue setup**
is reachable from the opened Activity's Plan task and still uses the same
canonical-state-derived workflow documented here.

The routine opened Activity is now organized as Plan, Prepare, Collect, Review,
Score, Share, and Advanced Activity tools. Assessment setup belongs under Plan;
actual Score judgment belongs under Score. The exact record-oriented menus remain
available under Advanced.

The same Information Density contract applies to every #66 task screen:
**Clearing/redrawing the screen is the default. Information remains visible only
when the teacher needs it to complete the current action.**

See `v0.3.0-task-oriented-activity-menus.md` for the complete #66 boundary.
