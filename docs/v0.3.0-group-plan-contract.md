# Concord v0.3.0 GroupPlan Contract

**Issue:** #50 — Define GroupPlan records and lifecycle
**Status:** Native record and lifecycle-service foundation implemented in issue #50
**Development version:** `pds-concord 0.3.0.dev0`
**Core requirement:** `pds-core>=0.6.1,<0.7`

## Purpose

`GroupPlan` is Concord's teacher-restricted planning layer between a roster and
canonical collaboration records. It is a proposal, not operational membership.

```text
Core roster / optional grouping_signal_set_v1
                    |
                    v
                GroupPlan
                    |
             preview / approve
                    |
                    | #56 only
                    v
          Group + GroupMembership
```

The permanent distinctions are:

```text
GroupPlan != Group
PlannedGroup != Group
planned_group_key != group_id
GroupPlan != GroupMembership
GroupingSignalSet != GroupPlan
band != Score
band != Grade
```

Direct Group creation remains first-class and does not require a GroupPlan.

## Native identity and history

The native record kind is:

```text
record kind: group_plan
identity field: group_plan_id
graph collection: group_plans
```

`group_plan_id` is the stable logical identity. Concord does not maintain a
second plan-version counter, mutable plan head, or GroupPlan-specific revision
directory. Existing native persistence supplies:

```text
stable group_plan_id
    -> immutable native record revision 1
    -> immutable native record revision 2
    -> ...
```

Each selected revision is also bound into the immutable Activity-work snapshot
chain. Historical GroupPlan revisions therefore use the same integrity,
expected-snapshot concurrency, and recovery rules as every other native Concord
record.

A GroupPlan is Activity-owned state. It is stored inside the Activity's existing
`ModuleWorkRef`; it is not a global or reusable-definition record.

## PlannedGroup

`PlannedGroup` is a nested plan-local value object:

```text
planned_group_key
label
student_ids
description          optional
effective_context    optional
```

`planned_group_key` is never a preallocated canonical `group_id`. Applying a
future approved plan must allocate fresh Group and GroupMembership identities.

Student identity is always the exact Core `student_id`. Names, email addresses,
case folding, fuzzy matching, and roster position are not identity authorities.

A plan may contain an empty PlannedGroup while it remains editable.

## Roster snapshot and coverage

Every GroupPlan revision records:

```text
roster_student_ids
```

This is a deterministic snapshot of the student IDs considered by the proposal,
not a copied Core roster record.

For every structurally valid GroupPlan:

```text
set(roster_student_ids)
==
set(students in proposed_groups)
UNION
set(unresolved_student_ids)
```

and:

- roster IDs are unique;
- each student appears in at most one PlannedGroup;
- unresolved IDs are unique;
- grouped and unresolved sets do not overlap;
- no roster student disappears silently.

Workflow services added later in #50 derive and validate the roster snapshot
against Core. Pure native graph validation deliberately performs no external
roster I/O.

## Strategy and targeting

Built-in v0.3 strategies are exactly:

```text
manual
imported_arrangement
random
similar_signal
mixed_signal
```

The record may carry one of:

```text
target_group_size
target_group_count
```

but never both. Generated non-draft random/signal proposals require exactly one
target. #50 records these inputs but does not implement a grouping algorithm.

`seed` is reserved for deterministic random plans. A non-draft random proposal
requires an explicit seed. Issue #52 now implements the exact
`pds-concord:group-plan-random:v1` SHA-256 ranking contract, exact size/count
target semantics, balanced partitioning, deterministic `random-N` plan-local
keys, and complete-roster draft generation. Random planning has no signal or
Meridian dependency.

## Optional Core signal binding

Signal-dependent plans may preserve exactly:

```text
source_signal_set_id
source_signal_set_digest
source_signal_dimension_id
```

These three values are all-or-none. The digest is lowercase SHA-256 of Core's
canonical `grouping_signal_set_v1` bytes, not the producer's
`source.snapshot_digest`.

Only `similar_signal` and `mixed_signal` plans may bind a signal. The GroupPlan
does not contain:

```text
student -> band mappings
raw grades
percentages
proficiency values
producer-native evidence
Meridian policy state
```

Core remains authoritative for the signal contract, serialization, immutable
exchange storage, digest, dimensions, and roster diagnostics. Concord has no
Meridian runtime dependency.

## Lifecycle contract

The native status vocabulary is:

```text
draft
previewed
approved
applied
cancelled
```

The intended transition graph is:

```text
draft -> previewed -> approved -> applied
  |         |            |
  +-------> cancelled <---+
```

`applied` and `cancelled` are terminal.

The model represents lifecycle provenance without providing a generic status
setter. The issue #50 lifecycle services enforce the transition rules below and
leave the `approved -> applied` mutation reserved for #56.

### Draft

Every new plan starts `draft`. Draft proposal content is editable.

A material edit to a previously previewed proposal creates a new native revision
and returns the current state to `draft`.

### Previewed

Preview is an explicit mutation, not a read side effect. The previewed revision
must be the exact persisted proposal presented to the teacher.

Before preview, the service must re-read the Core roster, reject roster drift,
validate exact student identities, and validate all Activity/Session context.

### Approved

Approval is a separate explicit mutation from `previewed`. Issue #55 now
revalidates signal-backed plans against the exact bound Core signal/dimension,
canonical digest, current roster, and current `missing_student_signal` findings.
Non-signal plans and signal plans using `manual` or `random` still require zero
unresolved students. A signal plan using `leave_unassigned` is the sole narrow
exception: its unresolved set must exactly equal Core's current missing set.

Approved proposal content is frozen against ordinary editing.

### Applied

The status exists now so the record contract is complete. Issue #50 must not
provide a generic mutation that marks a plan applied.

Only #56 may commit:

```text
approved GroupPlan
    + exact Group / GroupMembership write set
    -> applied GroupPlan
```

under the same Activity-work concurrency boundary.

### Cancelled

Draft, previewed, or approved plans may later be cancelled. Cancellation
preserves immutable history and creates no Group or Membership.

## Provenance

GroupPlan uses Concord's existing `Provenance` model:

```text
created_provenance
updated_provenance       optional
previewed_provenance     optional
approved_provenance      optional
cancelled_provenance     optional
applied_provenance       optional
```

Current-state provenance must agree with status. Historical native record
revisions retain earlier state and provenance.

Do not place signal bands, grades, or sensitive educational reasoning in
provenance notes.

## Cross-record validation

Native graph validation requires:

- the referenced Activity to exist;
- the GroupPlan Core class reference to equal the Activity class reference;
- every PlannedGroup EffectiveContext to reference Sessions from the same
  Activity.

Structural GroupPlan validation additionally enforces unique plan-local group
keys, exact proposal/unresolved coverage, target constraints, signal-binding
coherence, digest shape, strategy restrictions, and lifecycle-provenance
coherence.

External Core roster existence remains a workflow-layer check.

## Privacy and projection boundary

GroupPlan is teacher-restricted operational planning state. It is not a
publication projection.

GroupPlan data must not be copied into:

```text
default logs or support output
PDS2 route payloads
packet or Artifact metadata
ScoreRecord
Academic Result Manifest
Core Publication Record
```

Signal-backed plans retain only signal identity/digest/dimension, never bands.

Adding `group_plan` to Concord's generic native-record registry does not add it
to Academic Result Manifest generation or any publication producer contract.

## No canonical collaboration side effects

Native GroupPlan persistence alone creates zero:

- Groups;
- GroupMemberships;
- RoleAssignments;
- ResponsibilityAssignments;
- Artifacts or Artifact Pages;
- PDS2 routes;
- Scores;
- manifests;
- Publication Records.

Existing direct Group workflows remain unchanged.

## Implementation status

Issue #50 now includes both the native contract foundation and typed public
application services for:

```text
create
replace proposal
list/show
preview
approve
cancel
```

Reads are side-effect free. Proposal replacement is a full replacement boundary
that later #51/#52/#54 planners can target. Preview revalidates the exact Core
roster. Approval requires the previewed revision to remain the latest Activity
work change. Issue #55 adds exact signal revalidation plus the explicit
`leave_unassigned` unresolved-set exception; all other approval paths require
zero unresolved students. Approval creates no Group or GroupMembership.

Issue #51 now layers teacher-controlled manual authoring and direct
`student_id,group` arrangement import on this contract. It adds plan-local group
editing, exact roster-student placement/movement/unassignment, explicit
fail-closed roster refresh, deterministic strict CSV normalization, direct
`concord group-plan ...` commands, and a bounded teacher-menu planning path.
Those operations reuse this lifecycle and preserve the no-canonical-side-effect
boundary through approval.

Issue #52 now layers deterministic seeded random generation on the same contract.
It generates a complete draft from the exact Core roster, one explicit
size/count target, and an explicit seed, then leaves all editing, preview, and
approval behavior to the existing #50/#51 services.

Issue #54 now layers deterministic `similar_signal` and `mixed_signal` generation
on the same contract. Both consume one exact #53 signal/dimension selection, share
#52's full-roster size/count target semantics, preserve only exact signal
ID/Core-digest/dimension provenance, leave missing selected-dimension roster
students unresolved, and reuse #51 editing/refresh without rerunning the planner.
Direct CLI and teacher-menu creation remain draft-only and create no canonical
Group or GroupMembership.

Issue #55 now adds structured `missing_signal_disposition`, separate seeded
missing-only random distribution, explicit manual confirmation, deliberate
`leave_unassigned`, edit preservation, roster-refresh invalidation, and exact
approval-time Core revalidation. The disposition workflow does not copy bands or
a cached missing-student set into GroupPlan and never creates canonical state.

Canonical application remains reserved for #56; there is intentionally no
generic `apply_group_plan`, `mark_group_plan_applied`, or status setter.
