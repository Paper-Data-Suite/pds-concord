# v0.3.1 Generated Path Safety Foundation

**Issue:** #124 — Bound Concord-Owned Generated Paths and Output Filenames  
**Slice:** 1 — audit and bounded naming foundation  
**Baseline:** `fc282d8c96e7a0d6a12d70c362fea8da79f748d6`  
**Core qualification baseline:** released `pds-core 0.6.4`  
**Core wheel SHA-256:** `48cea9317f2967bdc0f2d4c14349a56677c7c3f8211f0f33978ccb1a1c75859b`

## Purpose

Slice 1 establishes a side-effect-free Concord naming primitive and records the
initial path-surface audit. It deliberately does **not** rename existing files,
rewrite canonical IDs, migrate workspaces, or change an existing writer.

The governing boundary is:

```text
Core-owned retained source
!=
Concord-owned generated output
```

Core 0.6.4 bounds newly written retained-source leaves and newly generated
`source_scan_id` values. Concord treats those stored values as opaque
provenance and does not reconstruct them from the original source filename.

For Concord-owned generated output:

```text
durable semantic identity stays durable
human-readable labels stay in metadata/content
generated output leaves use fixed names or bounded opaque tokens
```

## Bounded opaque token contract

`concord.generated_paths` defines the first reusable primitive.

The token is:

```text
cgo_<24 lowercase SHA-256 hex characters>
```

The digest input is a length-prefixed sequence containing:

```text
concord-generated-output-v1
domain
identity part 1
identity part 2
...
```

Length-prefixing prevents tuple-boundary ambiguity.

The generated token is always 28 characters. Generated opaque filenames use a
lowercase alphanumeric extension of at most 10 characters after the dot, so
the maximum opaque filename length is 39 characters.

The domain is part of the digest rather than the filename. This provides
domain separation without allowing namespace labels to expand the leaf.

The identity values themselves may be long because they are never copied into
the generated leaf.

Slice 1 does not yet define the separate bounded-human-readable filename policy
needed later by #114.

## Why Packet rendering is not changed in Slice 1

`PacketInstance.output_relative_path` is canonical stored state and existing
generated Packet outputs must remain readable.

Changing:

```text
rendered/packets/<packet_instance_id>.pdf
```

requires a prospective writer/read-compatibility design rather than a local
string substitution.

A later #124 slice should:

1. derive the new output leaf from exact Packet canonical identity through the
   bounded token helper;
2. preserve exact historical `output_relative_path` values;
3. keep deterministic re-render verification;
4. preserve create-only/conflict semantics;
5. qualify deep-workspace rendering from an installed wheel.

Slice 1 provides the primitive that migration can reuse.

## Why canonical durable-ID directories are not blindly hashed

Core's shared `validate_identifier()` is character-safe but does not impose a
general identifier-length limit.

That fact alone does not justify rewriting existing Concord canonical paths.

Canonical identifiers participate in:

```text
record identity
snapshot history
Packet/Template storage
Artifact relationships
route and output provenance
```

Hashing those paths without a migration design could break historical
readability.

Issue #124 therefore separates:

```text
generated output naming
```

from:

```text
canonical storage identity
```

and requires a reproduced need before changing the latter.

## Long-path policy

Concord does not use `LongPathsEnabled` as its application contract.

The suite regression that motivated Core 0.6.4 showed that native libraries can
fail on long paths even when Windows long-path policy is enabled.

#124 therefore uses:

```text
bounded generated components
+
representative deep-workspace qualification
+
real native-library installed acceptance where relevant
```

rather than claiming one universal safe absolute-path length.

Automated qualification must not modify Windows long-path policy.

## Slice 2 — prospective Packet rendered-output naming

Slice 2 applies the bounded generated-output contract to the first concrete
writer identified by the audit: Packet PDF rendering.

New Packet outputs use:

```text
rendered/packets/cgo_<24 lowercase SHA-256 hex>.pdf
```

The token is derived from the `packet-render` domain plus exact canonical:

```text
module_id
class_id
work_id
packet_instance_id
```

The Packet Instance ID remains the authoritative domain identity. The bounded
leaf is only filesystem identity.

### Historical compatibility

A generated `PacketInstance.output_relative_path` is authoritative for
re-rendering and opening.

Therefore:

```text
new rendering-state Packet
    -> derive new bounded output path
    -> render
    -> store exact output_relative_path + SHA-256

already-generated Packet
    -> use stored output_relative_path exactly
    -> re-render bytes
    -> verify stored SHA-256
    -> install/reuse at the stored historical path
```

The re-render path is **not recomputed** for an already-generated Packet.

This preserves historical outputs such as:

```text
rendered/packets/<packet_instance_id>.pdf
```

without rename or migration while new outputs receive bounded opaque leaves.

The existing #101 rendered-output opener already resolves the stored
`PacketInstance.output_relative_path`; it therefore remains compatible with
both historical and new Packet output names.

### Containment

The Packet writer now validates the selected target specifically beneath:

```text
rendered/packets/
```

rather than the broader `rendered/` directory.

PDF-only validation, symlink checks, deterministic byte comparison,
create/conflict behavior, and lifecycle persistence remain unchanged.

### No migration

Slice 2 does not:

- rename an existing Packet PDF;
- rewrite an existing `output_relative_path`;
- rewrite Packet Instance identity;
- change PDS2 routes;
- change rendered PDF content;
- change Artifact identity;
- change Template/Packet library storage.

### Next boundary

The next #124 slice should audit and harden the remaining Concord-owned
generated/staging surfaces under deep-workspace pressure, while leaving
canonical durable-ID storage unchanged unless a reproduced failure justifies a
separate compatibility design.


## Slice 3 — deep-workspace generated-surface qualification

Slice 3 adds real path-pressure qualification for the three current
Concord-owned generated-output families that participate directly in classroom
paper workflows:

```text
Packet rendered PDFs
returned-Artifact assemblies
Academic Result Manifest revisions
```

The synthetic workspace root is extended until its path is at least 120
characters before the operation-specific descendants are added.

This intentionally creates absolute output paths substantially longer than the
workspace root while keeping the domain identifiers ordinary and realistic.

The tests perform actual writes rather than only measuring strings.

### Packet rendering

The deep-workspace case performs real starter Packet rendering and verifies:

```text
rendered/packets/cgo_<24hex>.pdf
```

is written, is a real PDF, keeps the 32-character generated filename, and
replays from the stored output path without another canonical mutation.

This also exercises the `.packet-render.*.tmp` staging path used by the writer.

### Returned-Artifact assembly

The deep-workspace case performs a real image return through the existing route,
then assembles the returned evidence.

It verifies:

```text
assembly_<32hex>/
    artifact.pdf
    manifest.json
```

and replay of the exact assembly.

This also exercises the `.assembly.*` staging directory, fixed assembly leaves,
and the existing atomic directory install behavior.

The Artifact Instance ID remains a durable parent-path identity. Slice 3 does
not hash or migrate it because the generated assembly identity and leaves are
already bounded and the path-pressure operation is now explicitly qualified.

### Academic Result Manifest

The deep-workspace case creates an actual immutable Academic Result Manifest
revision and verifies the fixed numeric revision leaf:

```text
exports/manifests/academic_results/1.json
```

It then reloads the existing immutable revision.

The test exercises the existing `.write.lock`, create-only `os.open(...)`
revision write, fsync path, and canonical relative-path validation.

### Interpretation

Passing these tests means the remaining current generated surfaces do not have
a demonstrated need for another path-layout migration merely because their
surrounding canonical directories contain durable IDs.

That conclusion is deliberately narrower than claiming a universal maximum
safe Windows absolute-path length.

The application contract remains:

```text
do not depend on LongPathsEnabled for correctness
bound Concord-owned generated components
preserve durable semantic IDs
qualify representative deep workspace geometry
exercise native I/O where relevant
```

No test changes Windows registry or long-path policy.

### Next boundary

The next #124 slice should turn this source-level path-pressure evidence into an
isolated installed-wheel acceptance against the exact released Core 0.6.4
wheel, including Core retained-source compatibility and provenance.

## Slice 4 — installed Core 0.6.4 qualification

Slice 4 moves Concord's authoritative installed qualification baseline from
the exact released Core 0.6.3 wheel to the exact released Core 0.6.4 wheel:

```text
pds_core-0.6.4-py3-none-any.whl
SHA-256:
48cea9317f2967bdc0f2d4c14349a56677c7c3f8211f0f33978ccb1a1c75859b
```

This is a qualification-baseline change, not a runtime dependency-floor
change. `pyproject.toml` deliberately remains:

```text
pds-core>=0.6.3,<0.7
```

The dependency-floor decision remains release work for issue #111.

### Isolated installed acceptance

`scripts/smoke_test_generated_path_safety_wheel.py` builds an isolated virtual
environment, installs the exact authenticated Core 0.6.4 wheel plus the
candidate Concord wheel, runs `pip check`, and executes its acceptance code
under `python -I`.

The installed acceptance covers:

- deep-workspace bounded Packet rendering and exact replay;
- fresh bounded retained-source provenance written by Core 0.6.4;
- Concord routing of that exact Core provenance without filename
  reconstruction;
- deep returned-Artifact assembly with bounded assembly identity and fixed
  leaves;
- deep immutable Academic Result Manifest generation;
- historical Core 0.6 retained-source provenance whose retained filename and
  source-scan ID exceed the new Core 0.6.4 writer bounds;
- exact legacy path and source-scan identity preservation through Concord
  routing;
- no legacy rename, migration, or synthesized bounded replacement.

The historical compatibility case is intentionally placed in a shallow
workspace. Its purpose is reader compatibility for already-stored Core 0.6
provenance, not to require newly written long legacy paths to work at arbitrary
absolute path depth.

### Reader/writer asymmetry

Core 0.6.4 may write a new bounded retained-source name for the same original
filename, while Concord must continue to accept a historical retained path
already recorded in provenance.

Concord therefore treats these as distinct contracts:

```text
new Core write
    -> bounded Core-owned retained path and source_scan_id

existing Core provenance
    -> exact recorded path and source_scan_id remain authoritative
```

Concord does not derive retained-source identity from `source_filename`.

### Repository qualification repin

The existing installed-wheel smoke programs that asserted an exact Core
version are repinned to Core 0.6.4 so the authoritative repository validator
can execute coherently against one exact Core wheel.

This does not rewrite the historical issue documentation describing the Core
version used when those earlier issues were first qualified.

The package and release-artifact checks now also require
`concord/generated_paths.py` in the built candidate.

No dependency-floor change, workspace migration, registry modification, or
durable-ID migration is introduced by this slice.
