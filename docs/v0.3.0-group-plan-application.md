# Concord v0.3.0 Approved GroupPlan Application

**Issue:** #56 — Apply approved plans through native Group and GroupMembership services
**Status:** Implemented on the v0.3.0 development line
**Development version:** `pds-concord 0.3.0.dev0`
**Core requirement:** `pds-core>=0.6.1,<0.7`
**Exact Core qualification release:** `pds-core` v0.6.1

## Purpose

Issue #56 is the only GroupPlan workflow that converts teacher-approved planning
state into canonical collaboration state.

```text
approved GroupPlan
        |
        | exact application preview
        | explicit application identity
        | exact application digest
        | exact Activity snapshot
        v
canonical Group + GroupMembership
        +
applied GroupPlan revision
```

The transition is atomic. Concord never publishes only part of the requested
Group/GroupMembership write set and never marks a GroupPlan `applied` in a
separate transaction.

The permanent distinctions remain:

```text
GroupPlan != Group
PlannedGroup != Group
planned_group_key != group_id
GroupingSignalSet != GroupPlan
band != GroupMembership
```

Direct operational Group creation remains first-class and does not require a
GroupPlan.

## Public workflow surface

Issue #56 exports the typed presentation-neutral workflow:

```python
PrepareGroupPlanApplicationRequest
GroupPlanApplicationPreview
prepare_group_plan_application

ApplyGroupPlanRequest
GroupPlanApplicationResult
apply_group_plan
```

Preparation is read-only. Application is the guarded mutation.

No generic `mark_group_plan_applied`, status setter, prepared-application
database, reservation record, or second transaction exists.

## Eligibility

Only:

```text
GroupPlan.status == approved
```

is eligible.

`draft`, `previewed`, `cancelled`, and `applied` plans are rejected.

An applied plan is terminal. Reapplication is not a replay shortcut and Concord
does not replace or supersede canonical Groups on behalf of the plan.

## Exact application identity

Each application uses a fresh Core-valid `application_id`. When Concord
generates one, it uses a fresh `apply-<uuid4 hex>` identity.

Canonical Group and Membership identities are then deterministic functions of
that application identity and the approved plan contents.

Group domain:

```text
pds-concord:group-plan-application-group:v1
```

Group payload:

```text
domain
+ NUL + application_id
+ NUL + group_plan_id
+ NUL + planned_group_key
```

and:

```text
group_id = "group-" + sha256(payload).hexdigest()
```

Membership domain:

```text
pds-concord:group-plan-application-membership:v1
```

Membership payload:

```text
domain
+ NUL + application_id
+ NUL + group_plan_id
+ NUL + planned_group_key
+ NUL + student_id
```

and:

```text
membership_id = "membership-" + sha256(payload).hexdigest()
```

The full lowercase 64-character SHA-256 hexadecimal digest is retained.

The derivation does not use Python `hash()`, per-record UUID randomness,
filesystem ordering, wall-clock time, or iteration order.

A derived identity that already exists in the current Activity graph is a
conflict. Concord does not overwrite or reinterpret the existing record.

## Read-only exact application preview

`prepare_group_plan_application` performs no write and creates no workspace.

It:

1. loads the exact approved GroupPlan and current Activity graph;
2. requires the plan's exact Core roster snapshot still to equal the current
   Core roster;
3. for signal-backed plans, revalidates the exact signal ID, dimension, Core
   canonical digest, diagnostics, and current missing set through the existing
   #53/#55 boundary;
4. resolves the exact Membership context for every planned student;
5. derives all canonical Group and Membership IDs;
6. rejects identity collisions;
7. constructs and validates the complete hypothetical native candidate graph;
8. builds a deterministic semantic application manifest; and
9. returns the exact application digest and expected Activity snapshot.

Preparation does not create:

```text
Group
GroupMembership
GroupPlan revision
Activity snapshot
prepared application record
```

The same `application_id` and exact inputs reproduce the same preview.

## Application manifest and digest

The semantic preview marker is:

```text
record_type = group_plan_application_preview_v1
```

The manifest binds at least:

```text
application_id
class_id
activity_id
group_plan_id
GroupPlan native record revision
expected Activity snapshot revision
fallback EffectiveContext, when used
resulting GroupPlan status = applied
exact unresolved student IDs
exact canonical Groups
exact canonical GroupMemberships
```

Groups are ordered by `planned_group_key`. Memberships within a Group are ordered
by exact `student_id`.

The digest domain is:

```text
pds-concord:group-plan-application-preview:v1
```

The digest is:

```text
sha256(
    b"pds-concord:group-plan-application-preview:v1\0"
    + canonical_json_bytes(application_manifest)
).hexdigest()
```

The digest therefore changes if the application identity, plan revision,
expected snapshot, canonical identities, placement, group metadata, contexts,
fallback context, or unresolved population changes.

Commit-generated envelope metadata and provenance timestamps are not part of the
semantic preview digest.

## Snapshot and roster binding

The preview exposes the exact Activity snapshot revision it observed.

Final application requires that exact value as
`expected_snapshot_revision`. Any intervening Activity-work mutation causes a
conflict. Concord does not automatically recompute against `latest`, retry, or
force the application.

Both preparation and application require:

```text
current exact Core roster IDs
==
GroupPlan.roster_student_ids
```

Roster drift fails closed. Application does not refresh the plan, add newcomers,
drop departed students, or silently re-place students.

## Signal-backed revalidation

For `similar_signal` and `mixed_signal`, preparation and application reselect
exactly:

```text
source_signal_set_id
source_signal_dimension_id
```

through the existing Core-backed grouping-signal workflow and require the
current Core canonical digest to equal:

```text
source_signal_set_digest
```

Concord does not select a newer signal, import Meridian, query a producer, or
reconstruct producer-native academic evidence.

The current Core missing set is recomputed from
`missing_student_signal` diagnostics.

Application requires:

```text
complete signal coverage -> unresolved is empty
manual disposition       -> unresolved is empty
random disposition       -> unresolved is empty
leave_unassigned         -> unresolved exactly equals current Core missing set
```

No cached band map or cached missing-set copy is an application authority.

## PlannedGroup to canonical Group

Every approved `PlannedGroup` creates exactly one canonical `Group`, including an
approved empty PlannedGroup.

The mapping is:

```text
group_id = deterministic derived application Group ID
activity_id = GroupPlan.activity_id
label = PlannedGroup.label
status = planned
description = PlannedGroup.description
parent_group_id = None
effective_context = PlannedGroup.effective_context
```

`planned_group_key` remains plan-local identity and is not copied into the
canonical Group.

Existing Groups are not matched by label, membership, or apparent equivalence.
Application creates fresh Groups for this application identity and does not edit,
end, merge, or replace unrelated operational Groups.

## Student to canonical GroupMembership

Every exact student in `PlannedGroup.student_ids` receives exactly one canonical
Membership:

```text
membership_id = deterministic derived application Membership ID
group_id = corresponding canonical Group ID
participant_reference = exact Core student participant
status = active
effective_context = resolved exact Membership context
status_reason = None
supersedes_membership_id = None
```

A `leave_unassigned` unresolved student receives no Membership. Concord never
infers Memberships from `roster - assigned`.

## Effective Context

Canonical `GroupMembership.effective_context` is mandatory.

If a PlannedGroup already has an `effective_context`:

```text
Group effective_context = exact PlannedGroup context
Membership effective_context = exact same context
```

If a nonempty PlannedGroup has no context:

```text
Group effective_context = None
Membership effective_context = one explicit application-time fallback context
```

The fallback uses the existing native context vocabulary:

```text
one Session
several selected Sessions
a starting Session through the remaining Activity
```

No first/latest/current/all-session context is inferred.

One fallback applies to all contextless nonempty PlannedGroups in the same
application. Empty contextless groups require no fallback because they create no
Memberships.

## Atomic application transaction

After rederiving and verifying the exact preview, `apply_group_plan` constructs:

```text
applied GroupPlan revision
all canonical Groups
all canonical GroupMemberships
```

and calls the existing canonical storage primitive exactly once:

```python
commit_record_batch(
    ...,
    (
        applied_group_plan,
        *all_groups,
        *all_memberships,
    ),
    expected_snapshot_revision=preview.expected_snapshot_revision,
)
```

One successful application therefore advances exactly one Activity-work
snapshot.

The previous approved GroupPlan revision remains immutable in native history.
The new current snapshot exposes the applied GroupPlan, all Groups, and all
Memberships together.

Validation or concurrency failure before publication leaves the current snapshot
unchanged and creates no visible partial application state.

## Applied GroupPlan metadata

The terminal applied revision records:

```text
applied_provenance
applied_application_id
applied_application_digest
```

For `status == applied`, all three are required. For every other status, the two
application identity fields are absent.

The stored digest is lowercase SHA-256 and is the exact semantic application
preview digest the teacher or direct caller approved.

Concord does not persist a separate:

```text
planned_group_key -> group_id map
student -> membership_id map
student -> band map
```

Canonical IDs are reconstructible from the stored application identity and the
immutable plan contents.

Historical pre-#56 GroupPlan revisions remain readable because the two
application fields are optional unless status is `applied`.

## Privacy boundary

Canonical `Group` and `GroupMembership` records contain operational
collaboration facts only.

They must not copy:

```text
source_signal_set_id
source_signal_set_digest
source_signal_dimension_id
band
student band values
missing_signal_disposition
missing_signal_random_seed
missing_signal_disposition_provenance
GroupPlan.seed
target_group_size
target_group_count
planning strategy
signal ranking
teacher academic reasoning
producer / Meridian identity
```

Application provenance records the authorized actor and application time, not
sensitive planning rationale.

The application preview may show exact planned membership because the teacher is
explicitly reviewing the write set. It does not attach signal-band values to
those students.

## Direct CLI

Issue #56 adds:

```text
concord group-plan application-preview
concord group-plan apply
```

`application-preview` is read-only. It requires the exact class, Activity, and
GroupPlan identity, accepts an optional explicit `--application-id`, and uses the
normal Effective Context flags only when a fallback Membership context is
needed.

The output includes the exact:

```text
application ID
application digest
expected Activity snapshot
canonical Group IDs
canonical Membership IDs
unresolved IDs, when any
```

and writes nothing.

`apply` requires:

```text
--class-id
--activity-id
--group-plan-id
--application-id
--application-digest
--expected-snapshot
--actor-id
```

plus the exact same fallback-context flags when the preview required them.

There is no:

```text
--force
--skip-preview
--ignore-digest
--latest
--apply-anyway
```

A direct `apply` invocation carrying the exact preview identity/digest is the
caller's explicit mutation intent.

## Teacher menu

An approved GroupPlan exposes:

```text
Apply approved plan
```

The menu:

1. reloads and revalidates the approved plan;
2. asks for an explicit fallback context only when at least one nonempty planned
   group lacks a context;
3. generates a fresh application ID;
4. prepares the exact read-only application preview;
5. shows canonical Groups, Memberships, unresolved IDs, application ID, digest,
   and expected snapshot;
6. requires the exact confirmation word:

```text
APPLY
```

7. invokes the same typed `apply_group_plan` service; and
8. shows the resulting snapshot and counts.

Backing out before `APPLY` writes nothing.
