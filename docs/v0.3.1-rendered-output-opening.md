# v0.3.1 Rendered Packet Output Opening

**Status:** Implemented for issue #101.

Issue #101 adds a read-only teacher and direct-CLI boundary for opening an
already-rendered Packet PDF, or the controlled rendered-Packet directory, without
turning Open into another rendering or recovery operation.

## Authority

The authoritative output identity is the current canonical `PacketInstance`:

```text
PacketInstance.output_relative_path
PacketInstance.output_sha256
PacketInstance.generation_status
```

Concord does not discover an output by filename, modification time, directory
enumeration, or teacher-entered path. The exact current Packet Instance is
reloaded immediately before the final Open operation.

The presentation-independent boundary is:

```text
resolve_rendered_packet_output(...)
    ->
open_rendered_packet_output(...)
open_rendered_packet_output_directory(...)
```

The resolver returns `ResolvedRenderedPacketOutput` only after the existing file
has passed canonical-state, path, file-type, and SHA-256 verification.

## OPEN != RENDER / REPRINT

Open is strictly read-only with respect to Paper Data Suite state.

It may:

```text
load current Packet state
resolve the recorded relative output
validate the Concord work/output boundary
inspect link/reparse safety
hash the existing PDF
compare the hash with canonical output_sha256
request a local viewer/file-browser launch
```

It does not:

```text
render
re-render
reprint
repair
create a missing PDF
rewrite a tampered PDF
commit a Concord snapshot
allocate or rewrite a PDS2 route
record opened/printed/viewed state
```

`render_packet_instance(...)` remains the explicit authority for Render /
reprint and deterministic recovery.

## Path and integrity verification

The recorded relative path must remain under the exact Activity work identity:

```text
module: concord
class: <class_id>
work: <activity_id>
rendered/packets/<packet-instance>.pdf
```

Resolution reuses Core's safe module-work descendant authority and rejects
absolute substitution, traversal, escape, non-PDF targets, symlinked output,
and Windows symlink/junction reparse redirection. Generic cloud-placeholder
metadata is not treated as a symlink solely because it is a reparse point.

Immediately before Open, Concord computes SHA-256 over the existing bytes and
requires:

```text
SHA256(existing PDF) == PacketInstance.output_sha256
```

A missing or tampered output fails closed. Open does not search for a plausible
replacement and does not repair the derivative.

## Core local-open boundary

Only after successful verification does Concord delegate to:

```python
pds_core.local_open.open_local_path(...)
```

`LocalOpenError` becomes `ConcordWorkflowOpenError`. A viewer-launch failure is
therefore distinct from output-integrity failure: the Packet may remain valid
even when the operating system cannot launch its default handler.

## Teacher workflow

Routine teacher navigation is:

```text
Activity
-> Prepare
-> View prepared materials
-> Open one ready PDF
```

The same screen can open the verified rendered output folder for local
multi-file printing. Routine selection uses teacher-facing participant/group
labels and does not require Packet Instance IDs, raw student IDs, hashes, or
internal relative paths.

The advanced Packet workflow keeps these as separate actions:

```text
Render / reprint a Packet Instance
Open a rendered Packet
Open rendered Packet folder
```

After a successful generation, Concord presents a separate next-step Open menu
rather than automatically launching one or many PDF viewers.

When a generated output is missing or no longer matches its recorded digest,
the teacher is directed to `Render / reprint`. Open itself remains read-only.

## Rendered-folder semantics

`Open rendered Packet folder` is a teacher-local working convenience. It is not
a share-safe distribution boundary.

The folder:

```text
may contain outputs from more than one generation
is derived from a verified canonical Packet output
is never created by Open
is not a student distribution package
is not a co-teacher sharing package
```

Issue #114 owns bounded distribution packaging. Issue #110 owns
generation-wide rendering/reprinting optimization.

## Historical compatibility

Historical generated Packet outputs remain governed by their own stored
`output_relative_path` and `output_sha256`. Open does not load package-current
Template semantics and does not rerender an older Packet merely because a newer
Template Version now exists.

Existing v0.3.0/v0.3.1 workspaces require no migration for issue #101.

## Direct CLI

The deterministic direct commands are:

```text
concord packet instance-open
    --class-id ...
    --activity-id ...
    --packet-instance-id ...

concord packet instance-open-folder
    --class-id ...
    --activity-id ...
    --packet-instance-id ...
```

Both optionally accept `--workspace-root`. Neither accepts an arbitrary path,
URL, actor, expected write snapshot, or interactive selection. The explicit CLI
invocation is already the operator's request to Open.

## Privacy boundary

Opening a selected rendered Packet locally is an intentional teacher disclosure.
Routine Concord screens remain privacy-minimized and do not dump rosters,
student IDs, route payloads, hashes, canonical JSON, or relationship maps merely
because an output is being opened.

## Issue #101 installed-wheel acceptance

`scripts/smoke_test_rendered_output_opening_wheel.py` is the authoritative
isolated-wheel gate for this feature. It installs the candidate Concord wheel
with the exact released Core 0.6.3 qualification wheel and runs the acceptance
program under `python -I`.

The installed-only scenario proves:

```text
isolated site-packages provenance
fresh Core/Concord workspace
real class + roster + Activity
real think_pair_share starter installation
real reusable Packet creation
real Packet instantiation and PDS2 route registration
real PDF rendering
exact output path + SHA-256 resolution
fake local opener receives only the verified PDF/folder
Activity snapshot revision/SHA are unchanged by Open
Core route registrations are unchanged by Open
tampered output is rejected without viewer launch or repair
missing output is rejected without viewer launch or regeneration
```

The smoke is wired into `scripts/validate_repository.py` as:

```text
installed-wheel smoke: issue #101 rendered output opening
```

so the final v0.3.1 qualification issue #111 automatically carries this gate.

## Non-goals retained

Issue #101 does not implement #105 returned Artifact evidence opening, #110
generation-wide render/reprint optimization, #114 distribution packaging,
generic workspace browsing, arbitrary-path opening, upload/sharing, or print
history.
