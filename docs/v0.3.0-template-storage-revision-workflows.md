# Concord v0.3.0 Template storage and revision workflows

**Issue:** #58 — Implement Template Definition storage and revision workflows  
**Umbrella:** #47 — v0.3.0 Group Planning, Templates, Packets, and Guided Setup  
**Development version:** `pds-concord 0.3.0.dev0`  
**Core requirement:** `pds-core>=0.6.1,<0.7`  
**Status:** Implemented

## 1. Purpose

Issue #57 defined reusable `TemplateDefinition` and immutable `TemplateVersion`
semantics. Issue #58 makes those contracts a canonical, teacher-manageable
workspace library without placing reusable state under an Activity.

The implemented direction remains:

```text
Template Definition
    -> exact immutable Template Version
        -> later #62 Activity-specific generation
            -> fresh Artifact Instance
                -> fresh Artifact Page(s)
                    -> fresh Core PDS2 route(s)
```

Issue #58 stops at reusable library management. It does not instantiate an
Artifact, allocate an Artifact Page, register a PDS2 route, create a Packet,
copy an Activity, or perform scoring.

## 2. Canonical reusable authority

Reusable Templates are stored beneath the Core-resolved workspace at:

```text
shared/concord/templates/
```

They are deliberately **not** stored beneath:

```text
classes/<class_id>/modules/concord/work/<activity_id>/
```

The storage schema identifier is:

```text
concord_template_library_storage_v1
```

Each Template lineage owns an independent tree with immutable record revisions,
digest-linked snapshots, a guarded current-snapshot pointer, a write lock, and
exact rendering-specification bytes:

```text
shared/
└── concord/
    └── templates/
        └── <template_id>/
            ├── state/
            │   ├── library.json
            │   ├── records/
            │   │   ├── template_definition/
            │   │   │   └── <template_id>/revisions/<n>.json
            │   │   └── template_version/
            │   │       └── <template_version_id>/revisions/<n>.json
            │   ├── snapshots/<n>.json
            │   ├── current.json
            │   └── .locks/write.lock
            └── rendering-specifications/
                └── <rendering_specification_reference>.bin
```

No synthetic class, Activity, or `ModuleWorkRef` is created. There is no
canonical SQLite database and no mutable `latest`/`default` rendering alias.

## 3. Strict serialization and storage envelopes

`concord.template_serialization` performs exact typed conversion for
`TemplateDefinition`, `TemplateVersion`, and nested #57 dataclasses. Canonical
JSON is UTF-8, sorted, compact, newline-terminated, and rejects duplicate keys,
NaN/Infinity, unknown fields, missing required fields, and noncanonical round
trips.

Storage envelopes bind the schema, Template identity, record kind/identity,
independent storage `record_revision`, operation provenance, and exact typed
record body.

A Template Version's domain `revision_sequence` is separate from storage
history:

```text
Template Version != storage record revision
```

`revision_sequence` orders printable semantic successors. Storage revision
numbers preserve immutable persisted history for one logical record identity.

## 4. Rendering specification integrity

A `TemplateVersion` names an opaque `rendering_specification_reference` and exact
lowercase SHA-256 digest. Issue #58 stores the reviewed primary bytes under
`rendering-specifications/`.

Creation and revision inspect an ordinary non-link source file, read exact bytes,
capture device/inode/size/mtime plus SHA-256, build the typed Version, preview
that prepared state, and re-read the source before commit. A changed source is a
conflict. Symlinks and, where exposed by the platform, Windows reparse points
are rejected. Absolute source paths remain transient and are never persisted in
the reusable Template contract.

A rendering reference may reconcile only with byte-identical content. The same
reference with different bytes is a conflict.

## 5. Initial creation

`create_template_library` creates one Definition, one initial Version, exact
rendering bytes, record revision 1 for each record, snapshot 1, and
`current.json`.

Initial creation supports exactly:

```text
Definition draft + Version draft
Definition active + Version active/current
```

There is no implicit activation. The initial Version requires sequence 1, no
predecessor, matching Template identity/category, and rendering bytes whose
SHA-256 matches the Version contract. The current pointer is installed only
after immutable marker, records, rendering bytes, and snapshot verify.

## 6. Snapshots, head, and current Version

A per-Template snapshot selects the exact storage revision of every visible
Definition and Version and records:

```text
current_template_version_id
head_template_version_id
previous_snapshot_revision
previous_snapshot_sha256
```

`head_template_version_id` is the latest member of the single linear semantic
lineage. It may be a draft not yet selected.

`current_template_version_id` is the exact active Version selected for ordinary
future use. At most one Version may be active/current.

For example:

```text
v1 active/current
v2 draft/head
```

becomes, after explicit activation:

```text
v1 superseded
v2 active/current/head
```

No API substitutes an ambiguous "latest" rule for this distinction.

## 7. Successor revisions

`create_successor_template_version` appends a fresh immutable draft Version. It
requires exact `expected_snapshot_revision`, a fresh Version ID, sequence
`head + 1`, exact-head predecessor identity, matching Artifact category, exact
reviewed rendering bytes/digest, and a non-retired Definition.

Branching, gaps, duplicate IDs, cross-Template predecessors, and non-draft
successors fail closed. Creating a successor does not change current selection.

## 8. Activation

`activate_template_version` accepts only the exact draft lineage head. One
guarded mutation activates the candidate, supersedes the previous current
Version when present, promotes a draft Definition to active when needed, updates
`current_template_version_id`, and advances the Template snapshot once.

Historical Versions remain resolvable. Activation creates no Activity, Artifact,
ArtifactPage, Packet, RouteRegistration, Author, Subject, Review, Moderation,
Criterion, Score, or Publication record.

## 9. Definition metadata revision

`update_template_definition` permits only reusable `name`, `purpose`, and
`description` changes. Template identity, Artifact category, original
`created_provenance`, owner reference, and lifecycle status are immutable through
that workflow. Lifecycle changes use explicit lifecycle services.

An exact metadata no-op returns current state without another record revision or
snapshot.

## 10. Retirement

`retire_template_version` may retire a non-current draft Version. The active
current Version cannot be independently retired while the Template remains
active.

`retire_template` retires the Definition, retires the active current Version if
present, clears current selection, preserves head identity, and retains all
historical record revisions, snapshots, and rendering specifications.

Retirement is not deletion. Existing opaque historical
`ArtifactInstance.template_version_id` values remain valid even if a reusable
Template is absent or retired.

## 11. Concurrency, locking, and commit order

Every mutation after initial creation requires an exact positive
`expected_snapshot_revision`. There is no force overwrite and no silent retry.

A per-Template `state/.locks/write.lock` serializes mutation. Under that lock
Concord reloads/strictly verifies current state, rejects stale snapshots,
validates snapshot and record-history continuity, rejects orphan/colliding
history, writes and verifies immutable records/assets, writes and verifies the
next digest-linked snapshot, then atomically replaces `current.json`.

The current pointer is published last. If publication occurred but final
verification or lock cleanup fails, `TemplateStoragePartialSuccessError`
preserves bounded pointer/snapshot identity instead of claiming the mutation did
not happen.

## 12. Strict read surface

Issue #58 provides strict reads equivalent to:

```text
list_template_ids
load_current_template
list_template_versions
load_template_version
load_current_template_version
load_template_snapshot
```

Reads validate path/body identity, canonical JSON, record and snapshot digests,
predecessor links, exact lineage, head/current selection, lifecycle consistency,
and rendering bytes. Read-only listing creates no workspace state. Visible
malformed library entries fail closed. Teacher-facing ordering is deterministic
by `name.casefold()` and `template_id`.

## 13. Authoring transport

Teacher-authored structured input uses:

```text
concord_template_authoring_v1
```

It carries semantic Definition metadata for initial creation and semantic
Version content for initial/successor construction. It does not supply
authoritative created provenance, status, Version sequence, predecessor,
rendering digest, storage revision, or snapshot identity. Those are supplied or
derived by the workflow layer. Successor authoring omits Definition metadata.

## 14. Presentation-neutral workflow services

`concord.workflows.template` exposes:

```text
prepare_template_create / commit_template_create
prepare_template_revision / commit_template_revision
prepare_template_activation / commit_template_activation
prepare_template_update / commit_template_update
prepare_template_retire_version / commit_template_retire_version
prepare_template_retire / commit_template_retire
```

It also provides `list_templates` and `get_template`. Prepare performs review-time
validation without canonical mutation; commit revalidates sources and/or the
prepared Template snapshot before delegating to storage. The same services are
exported through `concord.workflows`.

## 15. Direct CLI

The fully noninteractive family is:

```text
concord template list
concord template show
concord template version-list
concord template version-show
concord template create
concord template revise
concord template activate
concord template update
concord template retire-version
concord template retire
```

Read commands need no class or Activity and create no workspace state. Initial
`concord template create` requires explicit Template/Version IDs,
`--authoring-file`, `--rendering-spec`, and actor provenance; `--activate` is
explicit.

Later mutations require:

```text
--expected-snapshot
```

That is a Template-library snapshot, not an Activity snapshot. Storage partial
success maps to exit code 4; stale snapshot and lock collisions map to conflict
exit code 3.

## 16. Teacher menu

The Concord main menu exposes a workspace-level:

```text
Template Library
```

The submenu provides list/select, create, Version history, successor creation,
activation, metadata update, Version retirement, and whole-Template retirement.
It needs no Activity selection and uses standard H/B/M/Q unwind behavior.

Teacher writes show bounded identity, head/current Version, Version label and
sequence, category, page count, return/privacy defaults, rendering
contract/reference/hash, and expected Template snapshot where applicable.
Writes require `CREATE`, `REVISE`, `ACTIVATE`, `UPDATE`, or `RETIRE`.
Cancellation commits nothing.

## 17. Privacy and identity boundary

Reusable Template state must not acquire concrete class, Activity, Session,
Group, Membership, GroupPlan, student, participant, `grouping_signal_set_v1`
contents/bands, Packet instance, Artifact, ArtifactPage, PDS2 route, scan,
Author, Subject, Review, Moderation, Criterion, Score, or Publication identity.

Only #57's identity-free defaults and compatibility metadata belong here. No
student-specific tree is created under `shared/concord/templates/`.

## 18. Existing Artifact compatibility

Issue #58 does not make existing opaque `ArtifactInstance.template_version_id`
values resolve through the reusable library as a condition of historical reads.

Issue #62 may require exact Template Version resolution when new Template-backed
Artifact/Page instances are generated; that future rule must not retroactively
invalidate older Artifacts.

## 19. Handoffs

Issue #59 now defines Packet contracts that exact-reference both `template_id`
and `template_version_id` without duplicating Template bodies. It also preserves
source-owned external components through typed Core `ModuleRecordRef` values.

Issue #60 should resolve those exact Template pairs through the #58 authority and
reuse accepted workspace-level shared-storage conventions where
appropriate without coupling Packet state to Template storage internals.

Issue #61's starter library must create Templates through #58 services.

Issue #62 owns exact Template Version resolution for Activity-specific
instantiation, fresh Artifact/Page identities, fresh PDS2 routes, effective
privacy resolution, and rendering.

Issue #63 may use exact reusable Template identities during Activity copying.
Issue #64 remains authority for reusable Role/Responsibility/Criterion/Scoring
Scale presets.

## 20. Qualification

Issue #58 qualification covers strict serialization, cross-Activity storage,
draft/active creation, immutable records and digest-linked snapshots, exact
rendering bytes, tamper detection, deterministic read-only listing, stale/lock
conflicts, linear successors, activation/supersession, metadata no-ops,
non-destructive retirement, orphan-history rejection, source races, direct CLI,
teacher menu, no Activity/route side effects, legacy opaque Artifact
compatibility, Ruff, strict Mypy, documentation/package validation, and complete
repository validation against the authenticated Core 0.6.1 wheel.

Physical paper round-trip acceptance is intentionally deferred because
Template-backed Artifact/Page generation remains #62.
