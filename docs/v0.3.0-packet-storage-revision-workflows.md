# Concord v0.3.0 Packet storage and revision workflows

**Issue:** #60 — Implement Packet Definition storage and revision workflows  
**Umbrella:** #47 — v0.3.0 Group Planning, Templates, Packets, and Guided Setup  
**Development version:** `pds-concord 0.3.0.dev0`  
**Core requirement:** `pds-core>=0.6.1,<0.7`  
**Status:** Implemented; Activity-specific Packet generation remains #62

## 1. Purpose

Issue #60 makes the reusable Packet contracts from #59 durable and
teacher-manageable without crossing into Activity-specific Packet generation.

The implemented reusable direction is:

```text
PacketDefinition
    -> exact immutable PacketVersion
        -> ordered PacketComponent(s)
            -> exact Concord Template Definition/Version references
            -> optional source-owned ModuleRecordRef values
        -> later #62 target-context resolution
            -> fresh Packet Instance
                -> fresh Artifact Instance(s)
                    -> fresh Artifact Page(s)
                        -> fresh Core PDS2 route(s)
```

Issue #60 owns reusable Packet persistence, revision history, lifecycle,
dependency validation, direct commands, and the teacher Packet Library.

It does not create Packet Instances, Artifacts, Artifact Pages, routes, Groups,
Memberships, Scores, or grouping-signal state.

The governing reusable contract remains the
[Packet Definition contract](v0.3.0-packet-definition-contract.md). Exact
Template dependencies resolve through the
[Template storage and revision workflow](v0.3.0-template-storage-revision-workflows.md).

## 2. Canonical workspace authority

Reusable Packet state is workspace-level:

```text
shared/concord/packets/
```

One Packet Definition lineage owns one directory:

```text
shared/
└── concord/
    └── packets/
        └── <packet_definition_id>/
            └── state/
                ├── library.json
                ├── records/
                │   ├── packet_definition/
                │   │   └── <packet_definition_id>/
                │   │       └── revisions/
                │   │           └── <n>.json
                │   └── packet_version/
                │       └── <packet_version_id>/
                │           └── revisions/
                │               └── <n>.json
                ├── snapshots/
                │   └── <n>.json
                ├── current.json
                └── .locks/
                    └── write.lock
```

The storage schema is:

```text
concord_packet_library_storage_v1
```

Reusable Packet state is not stored beneath:

```text
classes/<class_id>/modules/concord/work/<activity_id>/
```

Therefore:

```text
Packet library != Activity-native record graph
PacketDefinition != Activity
PacketVersion != PacketInstance
```

`PacketDefinition`, `PacketVersion`, and `PacketComponent` remain outside
Activity-native `RECORD_DESCRIPTORS`.

## 3. Strict Packet serialization

Issue #60 adds a dedicated reusable Packet serialization layer:

```text
concord.packet_serialization
```

It supports exact typed serialization for:

```text
PacketDefinition
PacketVersion
PacketComponent
PacketAudienceIntent
PacketCondition
PacketRenderingRules
ModuleRecordRef
Provenance
```

Canonical JSON is:

- UTF-8;
- deterministic;
- sorted by key;
- compact;
- newline-terminated;
- duplicate-key rejecting;
- NaN/Infinity rejecting;
- unknown-field rejecting;
- missing-field rejecting;
- exact typed-round-trip verified.

A canonical file is rejected when its path identity, storage-envelope identity,
and typed body identity disagree.

Packet contracts are not routed through Activity-native generic record
serialization merely to obtain JSON support.

## 4. Immutable storage revisions

Two reusable storage record kinds exist:

```text
packet_definition
packet_version
```

Each immutable persisted envelope binds:

```text
storage_schema_version
packet_definition_id
record_kind
record_id
record_revision
operation
operation_provenance
body
```

`PacketComponent` values remain nested immutable semantic state inside an exact
Packet Version. There is no separately mutable component registry.

The semantic and storage revisions are intentionally different:

```text
PacketVersion.revision_sequence
!=
record_revision
```

`PacketVersion.revision_sequence` describes the semantic Version lineage.

`record_revision` preserves immutable persisted history for one logical stored
record identity, including lifecycle-status changes.

## 5. Snapshot contract

Every Packet Definition lineage has one immutable contiguous snapshot history.

A snapshot binds:

```text
packet_definition_id
snapshot_revision
records[]
current_packet_version_id
head_packet_version_id
previous_snapshot_revision
previous_snapshot_sha256
operation
operation_provenance
```

Every selected record revision is bound by SHA-256.

Snapshots are:

- immutable;
- contiguous from revision 1;
- digest-linked to their exact predecessor;
- fail-closed on gaps;
- fail-closed on unexpected visible history;
- fail-closed on record digest mismatch;
- fail-closed on identity disagreement.

`current.json` is only a guarded pointer to one exact Packet snapshot:

```text
storage_schema_version
packet_definition_id
snapshot_revision
snapshot_sha256
```

It is not a mutable alias for "latest Packet Version."

## 6. Strict historical reads

Public storage reads include:

```text
list_packet_ids
load_current_packet
list_packet_versions
load_packet_version
load_current_packet_version
load_packet_snapshot
```

A read verifies the Packet library marker, guarded current pointer, snapshot
chain, selected record revisions, record digests, typed round trips, Version
lineage, current/head state, and lifecycle coherence.

Visible malformed Packet entries fail closed instead of disappearing from a
healthy-looking list.

Read-only listing does not initialize an absent Packet library or workspace
subtree.

Historical Packet reads validate Packet history without requiring sibling
modules to be installed and without re-resolving every source-owned external
record.

## 7. Head versus current Version

Issue #60 implements two explicit Version selectors.

```text
head_packet_version_id
```

identifies the newest semantic Version in the single linear lineage.

```text
current_packet_version_id
```

identifies the exact active Version selected for ordinary future use.

A valid reusable state can therefore be:

```text
v1 active/current
v2 draft/head
```

After activation:

```text
v1 superseded
v2 active/current/head
```

The implementation never infers current state from timestamp, filesystem order,
lexicographic identity, or highest visible filename.

## 8. Initial creation

`create_packet_library` creates one new lineage.

Supported initial lifecycle combinations are:

```text
PacketDefinition draft + PacketVersion draft
PacketDefinition active + PacketVersion active
```

The initial Version must have:

```text
revision_sequence = 1
supersedes_packet_version_id = None
```

Creation writes immutable marker/record/snapshot files first and publishes
`current.json` last.

Create-only identity collisions fail as conflicts.

## 9. Linear successor revisions

`create_successor_packet_version` creates one fresh draft successor.

It requires:

```text
expected_snapshot_revision
fresh packet_version_id
revision_sequence = head + 1
supersedes_packet_version_id = exact head
status = draft
```

A successor changes the head but does not implicitly change current selection.

Branching, sequence gaps, stale-head creation, duplicate Version identities, and
cross-lineage predecessors are rejected.

Semantic changes require a fresh Packet Version rather than an in-place rewrite.

## 10. Definition metadata updates

`update_packet_definition` may revise only reusable Definition metadata:

```text
name
purpose
description
```

The following are preserved:

```text
packet_definition_id
created_provenance
status
```

Lifecycle status uses explicit lifecycle operations instead of generic metadata
updates.

An exact metadata no-op creates no storage record revision and no new Packet
snapshot.

## 11. Exact Template dependency resolution

A `concord_template` Packet component contains both:

```text
template_id
template_version_id
```

Issue #60 resolves that exact pair through the canonical #58 Template library.

Resolution proves:

1. the Template Definition exists;
2. the exact Template Version exists;
3. the Version belongs to that exact Definition;
4. canonical Template storage passes strict validation;
5. the Definition/Version lifecycle is eligible for the requested Packet action;
6. reusable audience compatibility is not contradicted.

The Packet never substitutes:

```text
latest
current
newest
highest revision
```

and never copies the Template body into Packet storage.

### 11.1 Draft Packet authoring

A draft Packet Version may reference an exact Template Version whose status is:

```text
draft
active
superseded
```

provided neither the Template Definition nor exact Template Version is retired.

This permits coordinated reusable authoring.

### 11.2 Packet activation

Before activation, every exact Template dependency is re-resolved.

Activation requires each exact Template Version to be:

```text
active
superseded
```

and requires the Template Definition to be non-retired.

A draft Template Version therefore blocks Packet activation.

Later Template supersession does not rewrite the exact Packet reference.

Later Template retirement does not rewrite historical Packet state. Whether a
retired dependency remains eligible for a new Activity-specific generation is a
#62 decision.

## 12. Reusable compatibility checks

Issue #60 rejects reusable contradictions knowable without Activity context.

The current implementation validates Packet component audience intent against
the exact Template Version compatibility contract.

Role audience is compared to reusable participant compatibility because concrete
RoleAssignment resolution remains #62.

Checks that require concrete:

```text
Activity
Session
Group
participant
RoleAssignment
effective privacy
target cardinality
```

remain outside #60.

## 13. External component boundary

`external_component` stores a source-owned Core:

```text
ModuleRecordRef
```

Issue #60 strictly serializes and validates that reference.

It does not require the owning sibling module to be installed.

It does not claim:

```text
external record exists
external record is authorized
external record is renderable
external record is compatible with the target Activity
```

Therefore:

```text
valid ModuleRecordRef
!=
verified external record existence
```

No Quillan, ScoreForm, Meridian, or other sibling runtime dependency is added.

The referenced producer remains authoritative.

Any owner-supported resolution required for an actual Packet Instance remains
part of #62.

## 14. Activation

`activate_packet_version` activates only the exact draft lineage head.

Activation:

1. verifies exact expected Packet snapshot;
2. validates current reusable history;
3. re-resolves exact Template dependencies;
4. marks the prior active Version `superseded` when present;
5. marks the candidate `active`;
6. promotes a draft Packet Definition to `active`;
7. selects the candidate as current;
8. preserves the candidate as head;
9. advances exactly one Packet snapshot.

Activation never silently chooses an older draft or another Template Version.

## 15. Version retirement

`retire_packet_version` permits independent retirement only for a non-current
draft Version.

The active current Packet Version cannot be independently retired while the
Packet Definition remains active.

Retirement:

- preserves Version identity;
- preserves component references;
- creates an immutable storage revision;
- creates one Packet snapshot;
- does not delete historical files.

## 16. Whole-Packet retirement

`retire_packet` retires the reusable Packet Definition.

If a current active Version exists, it becomes retired in the same Packet
snapshot.

Whole-Packet retirement:

```text
definition.status = retired
current_packet_version_id = None
head_packet_version_id = preserved
```

All historical Versions and exact dependencies remain readable.

There is no reopen operation in #60.

## 17. Concurrency and locking

Every mutation after initial creation requires the exact:

```text
expected_snapshot_revision
```

This is a reusable Packet-library snapshot, not an Activity snapshot and not a
Template-library snapshot.

Mutations use:

```text
state/.locks/write.lock
```

Under the lock, Concord reloads and validates current Packet state before
planning immutable files.

A stale writer fails as an explicit conflict.

There is:

```text
no force overwrite
no silent stale retry
no last-write-wins behavior
```

Write-history validation also rejects unexpected snapshots, record identities,
record revisions, symlinks, junction/reparse traversal, and other visible
canonical-state anomalies before mutation.

## 18. Pointer publication and partial success

Immutable record revisions and the next immutable Packet snapshot are written
and verified before the current pointer is replaced.

`current.json` is atomically published last.

Issue #60 defines:

```text
PacketStoragePartialSuccessError
```

to distinguish:

```text
no canonical pointer publication
```

from:

```text
Packet pointer published but final verification/cleanup incomplete
```

The error preserves, when known:

```text
pointer_published
snapshot_revision
snapshot_sha256
```

The direct CLI maps this condition to structured partial-success exit code 4.

The teacher menu shows a bounded reconciliation message and does not silently
retry.

## 19. Packet authoring transport

Reusable Packet authoring uses:

```text
concord_packet_authoring_v1
```

The transport carries teacher-authored reusable semantics:

```text
definition:
    name
    purpose
    description

version:
    version_label
    components
    rendering_rules
```

Successor authoring omits Definition metadata.

Authoring does not accept authoritative:

```text
created provenance
lifecycle status
revision_sequence
predecessor identity
record_revision
snapshot identity
current/head identity
digest fields
```

Those are derived by Concord.

Prepared authoring files are fingerprinted and re-read at commit time. A changed
source after review is a conflict.

The transport is non-executable and contains no shell/Python expression
language.

## 20. Presentation-neutral workflows

The reusable workflow layer is:

```text
concord.workflows.packet
```

It exports typed read models plus prepare/commit operations for:

```text
list_packets
get_packet

prepare_packet_create
commit_packet_create

prepare_packet_revision
commit_packet_revision

prepare_packet_activation
commit_packet_activation

prepare_packet_update
commit_packet_update

prepare_packet_retire_version
commit_packet_retire_version

prepare_packet_retire
commit_packet_retire
```

Prepare operations are side-effect free.

Commit operations revalidate reviewed source/state and delegate canonical writes
to `concord.packet_storage`.

The direct CLI and teacher menu share this service layer.

## 21. Direct Packet CLI

Issue #60 adds the fully noninteractive family:

```text
concord packet list
concord packet show
concord packet version-list
concord packet version-show
concord packet create
concord packet revise
concord packet activate
concord packet update
concord packet retire-version
concord packet retire
```

Read commands require neither class nor Activity context and do not initialize an
absent workspace.

Initial creation requires explicit Packet Definition/Version identities,
authoring file, and actor provenance. `--activate` is explicit.

Every post-create mutation requires:

```text
--expected-snapshot
```

where the value is the exact reusable Packet snapshot.

Output includes bounded Packet/Version/component information. Exact Template
identity pairs and external owner/kind/record identities are visible without
dumping external record bodies.

## 22. Teacher Packet Library

The Concord main menu now includes the workspace-level:

```text
Packet Library
```

It requires no Activity selection.

The menu exposes:

1. list/select Packets;
2. create Packet;
3. view Packet and Version history;
4. create successor Version;
5. activate current Version;
6. update Packet metadata;
7. retire Version;
8. retire Packet.

Navigation uses the ordinary Concord H/B/M/Q semantics.

Writes use literal confirmation words:

```text
CREATE
REVISE
ACTIVATE
UPDATE
RETIRE
```

Cancellation commits nothing.

Packet previews display bounded ordered component information, including exact
Template references or external `ModuleRecordRef` identities, copies per target,
audience/role intent, requirement/condition state, rendering rules, and expected
Packet snapshot.

The Packet Library never selects an Activity target.

## 23. Privacy and planning exclusions

Reusable Packet storage contains no concrete:

```text
class identity

Group identity

Artifact identity

```

In particular:

```text
Packet audience intent != privacy authorization
Packet role intent != RoleAssignment
Packet Version != Packet Instance

```

Packet storage never consumes grouping signals and never records how an
operational Group was planned.

## 26. #62 generation handoff

Issue #62 receives an exact reusable Packet Version and owns operational
instantiation.

It must:

- re-resolve exact Packet/Template dependencies;
- decide new-generation eligibility for subsequently retired dependencies;
- resolve Activity/Session/Group/participant/role targets;
- evaluate bounded `PacketCondition` declarations;
- expand `copies_per_target`;
- preserve deterministic component/target ordering;
- create a fresh Packet Instance;
- create fresh Artifact Instances;
- create fresh Artifact Pages;
- allocate fresh Core PDS2 routes;
- bind Template rendering inputs;
- resolve effective privacy;
- preserve exact Packet/Template provenance;
- perform any owner-supported external-reference resolution required for
  generation.

It must not copy GroupPlan or grouping-signal internals into generated metadata.
