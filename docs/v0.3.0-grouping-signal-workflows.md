# Concord v0.3.0 Grouping-Signal Workflows

**Issue:** #53 — Implement grouping-signal discovery, import, and diagnostics
**Status:** Implemented on the v0.3.0 development line
**Development version:** `pds-concord 0.3.0.dev0`
**Core requirement:** `pds-core>=0.6.1,<0.7`
**Exact qualification release:** `pds-core` v0.6.1

## Purpose

Issue #53 is Concord's explicit teacher-facing bridge from Core's neutral:

```text
grouping_signal_set_v1
```

exchange to the signal-dependent GroupPlan strategies implemented by issue #54.

The implemented boundary is:

```text
Core immutable grouping signal
        |
        | #53
        v
explicit signal + dimension selection
        |
        | #54
        v
similar_signal / mixed_signal GroupPlan
        |
        | #55
        v
explicit missing-signal disposition
        |
        v
preview -> approve
        |
        | #56
        v
Group + GroupMembership
```

Issue #53 itself does not implement a grouping algorithm and does not create a
GroupPlan. Issue #54 now consumes this exact selection boundary to create
deterministic signal-backed drafts.

## Core remains authoritative

Concord composes Core's released public modules:

```python
pds_core.grouping_signals
pds_core.grouping_signal_csv
pds_core.grouping_signal_storage
pds_core.grouping_signal_diagnostics
```

Core owns the canonical model, JSON, `grouping_signal_csv_v1`, immutable exchange
storage, SHA-256 binding, exact class/student identity, and roster diagnostics.

Concord does not maintain a shadow signal model, duplicate CSV parser, duplicate
storage path grammar, digest sidecar reader, or second roster-comparison
algorithm.

The primary #53 workflow module is:

```python
concord.workflows.grouping_signal
```

and exposes presentation-neutral operations including:

```text
list_grouping_signals
inspect_grouping_signal
select_grouping_signal_dimension
inspect_grouping_signal_csv_file
prepare_grouping_signal_csv_import
import_grouping_signal_csv
```

Transient Concord summary/selection/import values are not persisted native
records.

## Exact discovery

Discovery is scoped to one explicit Core class. `list_grouping_signals` first
requires that exact Core class and then delegates identity enumeration and
loading to Core.

One immutable snapshot is identified by:

```text
(class_id, signal_set_id)
```

There is no Concord concept of:

```text
latest signal
current signal
active signal
newest signal
default signal
```

Listing is deterministic for presentation only. Ordering never implies
selection.

A valid class with no signals returns an empty collection. A missing class is
not treated as an empty signal collection.

Core storage corruption or digest failure fails closed rather than being
silently skipped.

## Exact inspection and digest identity

`inspect_grouping_signal` loads one exact signal through Core and immediately
runs Core diagnostics against the current exact class roster.

The inspection preserves the Core `StoredGroupingSignal`, including:

```text
digest_algorithm = sha256
digest = <canonical Core signal digest>
```

This digest is not the same concept as producer provenance:

```text
source.snapshot_digest
```

The Core signal digest binds the canonical `grouping_signal_set_v1` bytes.

`source.snapshot_digest`, when present, binds whatever upstream snapshot the
producer identified.

Concord displays these separately and signal-backed GroupPlan provenance uses the
Core signal digest for:

```text
source_signal_set_digest
```

## Explicit dimension selection

A signal may declare several independent dimensions.

Concord never:

```text
selects the first dimension
selects the alphabetically first dimension
combines dimensions
averages bands across dimensions
treats equal band numbers across dimensions as equivalent
```

`select_grouping_signal_dimension` requires the exact:

```text
class_id
signal_set_id
dimension_id
```

and returns the exact Core signal, canonical digest, selected dimension, and
Core diagnostic report.

This is the signal-resolution handoff consumed by issue #54.

Selection is transient and read-only. Concord does not persist:

```text
selected signal
current signal
selected dimension
default dimension
Activity signal binding
workspace signal preference
```

## Core diagnostic semantics

Issue #53 preserves Core's released diagnostic codes:

```text
class_mismatch
wrong_class_student
unknown_student
missing_student_signal
```

Their policy boundary is:

```text
class_mismatch         -> error
wrong_class_student    -> error
unknown_student        -> error
missing_student_signal -> warning / valid partial coverage
```

An error makes the signal unusable for the #54 planning handoff until the
teacher chooses or imports a usable signal.

A missing signal is not:

```text
band 0
band 1
failure
absence
unenrollment
low proficiency
permission to omit a student
```

Missing-signal planning policy belongs to issue #55.

Diagnostics use exact Core `student_id`. Names, email, case folding, fuzzy
matching, and roster position are not identity authorities.

## Privacy-bounded diagnostics

Normal discovery and inspection are metadata/count oriented.

The direct and teacher-menu diagnostic views may expose exact IDs only when they
identify a condition the teacher explicitly asked to diagnose:

```text
missing student IDs
wrong-class student IDs
unknown student IDs
```

Correctly matched per-student band assignments are not emitted by normal
`list`, `show`, or diagnostic summary output.

Band distributions use neutral labels:

```text
Band 1
Band 2
...
Band N
```

Concord does not add ability, proficiency, readiness, or performance labels to
Core ordinal bands.

## Teacher-controlled CSV import

Issue #53 imports only Core's existing:

```text
grouping_signal_csv_v1
```

format. Concord does not define a second signal CSV contract.

The service pipeline is:

```text
explicit local file
    |
    v
Core structural CSV parse
    |
    v
Core CSV -> GroupingSignalSet conversion
    |
    v
exact requested-class diagnostics
    |
    +--> Core errors -> reject, no write
    |
    +--> missing-only warnings -> visible, allowed
    |
    v
canonical digest preview
    |
    v
Core write_grouping_signal
```

The source file may live outside the PDS workspace because the teacher selects
it explicitly. Concord requires a readable regular file, never modifies the
source, never derives identity from its path/name, and never persists the local
path as signal provenance.

Manual file selection does not rewrite Core provenance. A CSV carrying:

```text
source.kind = module_generated
source.module_id = meridian
```

remains module-generated provenance. It does not cause Concord to import or
invoke Meridian.

## Complete signals versus dimension projections

For:

```text
representation_scope = complete_signal
```

the CSV-declared identity is preserved:

```text
signal_set_id
created_at
class_id
source
dimension
student bands
```

Projection-only identity overrides are rejected for a complete signal.

For:

```text
representation_scope = dimension_projection
```

Core requires a new standalone identity because the CSV contains only one
dimension selected from a larger source snapshot.

Concord therefore requires explicit:

```text
new_signal_set_id
new_created_at
```

as a pair before standalone conversion. The new timestamp must be
timezone-aware. Core remains responsible for rejecting reuse of the source
multi-dimensional identity.

## Import validation and atomicity

Before any Core write, Concord completes:

```text
regular-file read
Core CSV structural validation
complete/projection identity validation
exact target-class validation
Core roster diagnostics
canonical digest calculation
```

Core diagnostic errors reject the candidate:

```text
class_mismatch
wrong_class_student
unknown_student
```

Missing-only partial coverage does not reject it.

Structural failures such as duplicate rows, malformed metadata, invalid bands,
invalid identifiers, unsupported schema/type values, or malformed provenance
are Core validation failures and create no signal.

Core immutable write semantics remain:

```text
new identity + canonical contents      -> created
existing identity + identical contents -> existing
same identity + different contents     -> conflict
```

Concord never overwrites or revises an existing grouping-signal identity.

## Review-to-write digest binding

The teacher menu separates preparation from persistence so the complete
candidate can be reviewed before `IMPORT`.

`prepare_grouping_signal_csv_import` returns the exact canonical digest shown to
the teacher.

The confirmed write carries:

```text
expected_signal_digest
```

and `import_grouping_signal_csv` reparses/revalidates the source file. If its
canonical candidate digest changed after preview, the write fails closed:

```text
Grouping-signal CSV changed since preview
```

No Core signal is written in that case. This prevents a valid file from being
changed between review and confirmation without another teacher review.

The direct CLI does not need a separate confirmation phase: invoking the
noninteractive mutation is itself explicit write intent, and the same validation
pipeline runs immediately before the Core write.

## Direct CLI

Issue #53 adds:

```text
concord grouping-signal list
concord grouping-signal show
concord grouping-signal diagnose
concord grouping-signal import-csv
```

Every action requires:

```text
--class-id
```

and supports the normal optional:

```text
--workspace-root
```

### `list`

Lists exact immutable signal identities, creation time, bounded source
provenance, declared dimensions, and Core canonical digest.

It does not print student-band rows.

### `show`

Requires:

```text
--signal-set-id
```

and shows exact identity, Core digest, source provenance, dimensions/band counts,
and diagnostic error/warning counts.

It does not choose a dimension and does not dump student-band rows.

### `diagnose`

Requires:

```text
--signal-set-id
--dimension-id
```

and reports roster/entry/matched/missing/wrong-class/unknown counts, neutral band
distribution, and exact problem IDs when present.

It is an informational command: diagnostic errors are reported rather than
hidden so the teacher can see why a signal is unusable for later planning.

### `import-csv`

Requires:

```text
--csv-path
```

A dimension projection additionally requires:

```text
--new-signal-set-id
--new-created-at
```

The command is class-level Core exchange mutation. It does not require an
Activity ID, actor, or Activity expected-snapshot revision because it creates no
Concord Activity-work record.

Output is bounded to import disposition, signal/class identity, Core digest,
source, dimension, matched/missing counts, and warning count.

## Teacher menu

The existing Activity `Plan groups` path now exposes:

```text
Grouping signals
```

with:

```text
List signals
Inspect / diagnose a signal
Import grouping-signal CSV
```

Signal and dimension selection are both explicit. The menu does not auto-select
the only/newest/first signal or first dimension.

Import uses structural preflight before projection identity prompts, then the
full read-only preparation service before write confirmation. Validation errors
therefore do not reach an `IMPORT` prompt.

A missing-only signal is shown as partial coverage, including exact missing IDs,
and may be imported after the teacher explicitly confirms:

```text
IMPORT
```

The menu preserves existing H/B/M/Q navigation semantics.

## No Activity or GroupPlan mutation

Grouping signals are Core class-level exchange records.

Issue #53 discovery, inspection, diagnostics, selection, and import do not:

```text
create or revise an Activity
create or revise a GroupPlan
bind a signal to a manual/random GroupPlan
create a Group
create a GroupMembership
create a RoleAssignment
create a ResponsibilityAssignment
```

Issue #54 now creates signal-backed GroupPlan drafts through a separate planning
workflow. The #53 discovery/inspection/diagnostic/import operations documented in
this section remain nonmutating with respect to Activity and GroupPlan state.

Issue #55 owns missing-signal planning disposition.

Issue #56 owns approved-plan application to canonical Group/Membership state.

## Producer neutrality and sibling isolation

`source.module_id` is provenance, not dispatch.

Production and required #53 tests do not require:

```text
pds-meridian
pds-scoreform
pds-quillan
pds-vitrine
pds-portia
paper-data-suite
```

A conforming module-generated Core signal can be discovered and imported without
the named producer installed.

Meridian remains a future producer, not a Concord runtime dependency.

## Relationship to existing GroupPlan strategies

Manual, imported-arrangement, and random GroupPlans remain fully usable with
zero grouping signals.

Issue #53 does not alter their lifecycle, roster refresh, direct CLI, or
teacher-menu behavior.

The implemented #54 signal-backed strategies preserve only:

```text
source_signal_set_id
source_signal_set_digest
source_signal_dimension_id
```

inside GroupPlan. Student-band mappings remain in the Core signal rather than
being copied into the plan.
