# v0.3.1 Student Feedback Distribution

**Issue:** #114  
**Status:** Implemented; final installed-wheel qualification required by this document.

## Purpose and source authority

Student Feedback Distribution turns the current student-target Score semantics
for one Activity into a bounded local package that a teacher can print or share
through channels outside Concord. It is a derived-output workflow, not Academic
Result publication and not a second academic database.

One logical preparation starts from **one exact ActivityReadContext**. The
authoritative Score population is the **current Score lineage heads** from that
exact verified Activity snapshot plus the current Core roster. The preparation
path loads the Activity graph once and the Core roster once, then builds reusable
Score/target indexes for roster-wide projection. No persistent analysis or
distribution cache is created.

Only a Score whose target satisfies:

```text
ScoreTargetReference.target_kind == "core_student"
owning_system == "core"
```

can become student feedback. Group, Artifact, Session, and Activity Scores stay
their own target kinds. Group membership, Artifact Author, and Artifact Subject
identity never fan out or substitute for Score target identity.

Issue #123 Target Detail is teacher-local. #114 may reuse the already-defined
current-score semantics behind that analysis, but it does not distribute
`target_detail.pdf` and does not expose its teacher-local technical material.

## Share-safe projection

The immutable `StudentFeedbackProjection` contains only student-facing
semantics. Each `StudentFeedbackResult` contains:

- Criterion label;
- Scoring Scale name;
- exact native Scale value and value label for a scored result; or
- the exact non-score disposition.

The allowed non-score dispositions remain:

```text
insufficient_evidence
absent
excused
not_observed
not_applicable
deferred
```

They are not converted to zero, failure, or missing work. A roster student with
no current student-target Score is **no distributable feedback**, not an inferred
academic status.

The projection excludes raw student IDs, Score IDs, Criterion IDs, Scale IDs,
Session IDs, snapshot hashes, source paths, Evidence Links, teacher rationale,
Moderation detail, peer identity, history, and provenance. There is no Grade or standards-proficiency inference,
no mastery or percentage conversion, and
no required Criterion × student matrix.

## Preview, selection, and teacher review

Preview is zero-write. Whole-class review distinguishes roster count,
distributable feedback, no-feedback students, unresolved students, requested
students, and the selected output set.

All-roster preparation preserves authoritative Core roster order. If any roster
student cannot be included, Concord never silently drops that student. The menu
requires the literal decision:

```text
PREPARE AVAILABLE ONLY
```

before a reviewed available-only plan can be created.

Selected-student mode requires exact current Core roster identity. Unavailable
or unresolved selected students fail the request rather than being silently
omitted. Output remains in roster order even when the caller supplies selected
IDs in another order.

## Reviewed plan and currentness

`PreparedStudentFeedbackDistribution` binds the exact class/Activity identity,
`expected_snapshot_revision`, `expected_snapshot_sha256`, selection mode,
roster/request order, unavailable partitions, exact share-safe projections,
destination, managed filenames, and a deterministic **reviewed plan digest**.

`created_at` is package provenance, not semantic plan identity.

A new package requires literal:

```text
PREPARE
```

Execution verifies the reviewed plan, renders only from that immutable plan,
and performs a **last-safe-point currentness check** immediately before the first
durable staging mutation. If the Activity has advanced, the old plan fails
before new package bytes are created.

An already-installed exact historical package is different: if it fully
self-verifies against the same reviewed plan digest and managed output set, it
may be reused without rerendering and without asking whether the source Activity
is still current. A **historical package** remains a truthful snapshot of the
source state it records.

## Package contract

A successful distribution contains exactly:

```text
one individual PDF per selected student
Print All Feedback.pdf
Feedback Index.html
distribution-manifest.json
```

The individual PDFs are student-scoped. The aggregate PDF/index/manifest are
staff-scoped class-set artifacts. The package directory as a whole therefore
must not be described as globally student-safe.

Every individual filename is created through
`build_human_readable_output_filename(...)` from issue #124. #114 introduces no
second filename sanitizer, truncator, or hash naming policy. Duplicate,
case-colliding, long, Unicode, punctuation-heavy, and Windows-hostile display
names remain bounded and deterministic without exposing raw student IDs.

`Print All Feedback.pdf` is the roster-ordered concatenation of the same
student-safe PDF semantics. Its page count is verified against the represented
individual pages.

`Feedback Index.html` is static: relative links only, no server, no JavaScript
requirement, no remote resources, and no links back into the Concord workspace.
It contains only selected students.

`distribution-manifest.json` uses the versioned
`concord_feedback_distribution_v1` contract. It records source snapshot
identity, counts, ordering rule, reviewed plan digest, opaque per-entry identity,
student display name, projection digest, output filename/digest/page count and
audience scope, plus aggregate/index digests and the package digest. It contains
no raw student IDs, Score records, Evidence Links, retained paths, routes,
PDS2 payloads, credentials, or unavailable/unselected student identities.

## External destination and installation

The final destination is an explicit teacher-controlled absolute path outside
the Paper Data Suite workspace. Lexical parent traversal, filesystem-root
destinations, source/output overlap, unsafe existing destination objects, and
redirecting symlink/junction ancestry fail closed.

Creation follows:

```text
preflight
-> last-safe-point currentness check
-> private sibling staging
-> exclusive file writes
-> complete package verification
-> atomic no-replace final promotion
-> final verification
```

Final promotion must never overwrite a destination that appears during a race.
Windows uses its non-replacing rename behavior; Linux uses
`renameat2(..., RENAME_NOREPLACE)`; Darwin uses
`renamex_np(..., RENAME_EXCL)`; unsupported platforms fail closed instead of
falling back to replacing rename behavior.

A conflicting destination is preserved and rejected. Partial filesystem failure
is never reported as successful completion. Staging cleanup is best-effort and a
cleanup failure is surfaced explicitly.

## Verification and opening

The read-only verifier proves manifest schema, exact managed file set, no extra
file, all SHA-256 values, individual/combined PDF existence and page counts,
static relative index containment, reviewed plan digest, and package digest.

Changing one managed PDF, deleting a file, or adding an unexpected file makes
the directory non-pristine.

Opening a verified distribution folder or `Print All Feedback.pdf` delegates to
`pds_core.local_open.open_local_path`. Opening is read-only. Viewer failure
does not rewrite the package or create academic state.

## Menu and direct CLI

The teacher path is deliberately under the existing Activity Share task:

```text
Open Activity
-> Share
-> Student feedback distribution (local package)
```

It remains visibly distinct from Core Academic Result publication.

The deterministic direct CLI uses the same services:

```text
concord feedback distribution-preview
concord feedback distribution-prepare
concord feedback distribution-verify
```

`distribution-preview` is zero-write and prints the exact review digest.
`distribution-prepare` rebuilds the current plan from the same explicit
class/Activity/selection/destination inputs, requires that digest, and still
requires literal `PREPARE`. `distribution-verify` is read-only and may verify a
historical package independently of current source state.

## Non-goals and privacy boundary

#114 provides no email integration, no Gmail/Outlook sending, no cloud permission management,
no ACL changes, no hosted portal, and no delivery state. Preparing or opening a
package does not prove that anything was printed,
sent, shared, received, opened, read, or discussed.

Package creation mutates no Concord canonical Activity/Score state, no Core
publication state, and no routing state. Existing valid workspaces require no
migration solely for #114.
