# v0.3.1 Artifact Attribution Batching

**Status:** Implemented for issue #106.

Issue #106 makes routine Artifact attribution fast enough for ordinary classroom
collection without changing Concord's provenance model. The teacher can review
current Author and Subject proposals together, confirm many straightforward
relationships in one reviewed operation, handle genuine exceptions individually,
and create several same-semantics student relationships in one atomic add.

## Architectural boundary

The governing invariant remains:

```text
Artifact Author != Artifact Subject
```

An `ArtifactAuthor` records who produced, completed, recorded, or represented the
work. An `ArtifactSubject` records whom or what the work concerns. They remain
independently zero-to-many, may identify the same person or different people, and
are never inferred from one another, routing, Group Membership, Role Assignment,
or Score targets.

Issue #106 changes orchestration and teacher interaction only. It does not replace
ADR 0005, add `student_id` to Artifact, or introduce a second attribution model.

## Review attribution

Routine Collect now exposes:

```text
Review attribution
```

The read-only projection groups current Author and Subject attention by Artifact.
Straightforward current `proposed` relationships are revalidated against current
semantics and shown as confirmation candidates. Disputed, unresolved, unknown,
invalid, conflicting, historical, and superseded relationships are not swept into
a bulk operation.

Already-confirmed relationships contribute only compact resolved counts rather
than dominating the routine screen.

The teacher actions are:

```text
A. Confirm all straightforward proposals
S. Select multiple proposals
C. Create several relationships
E. Review / edit attribution in Advanced tools
```

Long selectable proposal lists reuse Concord's shared ten-row paginated
multi-select interaction. Internal association IDs remain hidden from routine
teacher selection.

## Atomic batch confirmation

The typed status-only service is:

```text
BatchConfirmArtifactAttributionRequest
    -> batch_confirm_artifact_attribution(...)
```

One exact current Activity graph is loaded. Every requested Author and Subject is
required to be current, still `proposed`, semantically valid, and free of a
conflicting current equivalent. Only after all selected relationships pass does
Concord call `commit_record_batch` once.

A reviewed batch therefore produces:

```text
N Author/Subject status revisions
-> one canonical commit
-> one snapshot advancement
```

The service does not loop through the existing single-record update workflows.
Association IDs remain unchanged. Author/Subject references, authorship/Subject
roles, represented Group, Role context, representation status, Criterion context,
source metadata, privacy, and provenance remain unchanged. No `CorrectionRecord`
is created for simple confirmation.

The structural acceptance fixture proves both a one-relationship batch and a
large Activity-wide batch retain one full-state load and one canonical commit.
The large fixture contains:

```text
20 Artifacts
20 proposed Authors
20 proposed Subjects
40 relationships
```

All 40 relationships are confirmed with one canonical commit and one snapshot
advancement.

## Exceptions and cancellation

`Confirm all straightforward proposals` excludes disputed Authors, disputed or
unresolved Subjects, historical/superseded relationships, invalid references,
contradictory current relationships, and anything requiring semantic correction.
Those items remain visible for individual review.

Explicit subset selection binds exactly the displayed candidate relationships to
the reviewed snapshot. Canceling before the final `CONFIRM` produces no mutation.
If canonical state advances before commit, stale-snapshot protection rejects the
whole operation without partial confirmation.

## Homogeneous multi-add

`Create several relationships` supports common same-semantics Core-student cases:

```text
several student Authors on one Artifact
several student Subjects on one Artifact
```

The teacher chooses one Artifact, selects several roster students with the shared
multi-select helper, chooses one shared relationship configuration, reviews one
summary, and types one `ADD`.

Generated native Author/Subject association IDs are internal and are not requested
from the teacher. Every selected student is resolved against the authoritative
Core roster before the write. Equivalent-current duplicates, within-request
duplicate students, invalid context, or stale snapshots reject the entire batch.
All records in one multi-add share one provenance timestamp and are published in
one `commit_record_batch(...)` operation.

Routine multi-Author creation deliberately excludes heterogeneous and complex
cases such as recorder-for-Group, teacher/adult authorship, and collective Group
authorship. Routine multi-Subject creation is limited to homogeneous Core-student
Subjects. Those richer cases remain available through Advanced attribution tools.

## Recorder, Group, and identity preservation

Existing recorder-for-Group confirmation remains status-only. The represented
Group, Role Assignment, and representation status survive batch confirmation
unchanged. Collective Group Authors, unknown Author state, Group/Session/Activity
Subjects, external Subjects, and correction history continue to use the existing
single-record semantic authorities.

A person explicitly recorded as both Author and Subject remains two associations.
A peer observation with Student A as Author and Student B as Subject remains two
different identities. No cross-inference is performed.

## Attention and downstream boundaries

Confirmed straightforward proposals naturally disappear from collection
attention because the existing issue #67 attention contract reads current Author
and Subject statuses. Disputed and unresolved exceptions remain attention-worthy.

Attribution confirmation or multi-add does not create or revise:

```text
Artifact Review
ModerationRecord
ScoreRecord
ScoreEvidenceLink
Grade
Publication
returned evidence or assembly lineage
```

## Advanced and direct compatibility

The complete Author and Subject record-management menus remain reachable through:

```text
Advanced attribution tools
```

Existing deterministic direct CLI commands remain unchanged and noninteractive.
Issue #106 does not require a new batch CLI command.

## Existing workspace compatibility

Issue #106 introduces no new canonical attribution record type and requires no migration.
Existing `ArtifactAuthor` and `ArtifactSubject` records, immutable
history, correction lineage, returned work, and existing workspaces remain valid.
Batch confirmation writes ordinary new record revisions using the same status and
storage contracts already used by single-record updates.

## Qualification

Focused qualification covers semantic preservation, exception exclusion, stale
and invalid atomic rejection, explicit subset pagination, recorder-for-Group
preservation, Core roster enforcement, multi-add duplicate rejection, attention,
and the Activity-wide 20-Artifact / 40-relationship structural case.

`scripts/smoke_test_artifact_attribution_batch_wheel.py` is the authoritative
Issue #106 isolated-wheel gate. It installs the candidate Concord wheel with the
exact released Core 0.6.3 qualification wheel, runs `pip check`, and executes the
teacher acceptance scenario under `python -I`.

The installed-only scenario proves:

```text
isolated site-packages provenance
synthetic class / roster / Activity / Artifacts
multiple proposed Authors and Subjects
one unresolved Subject exception
Review attribution teacher flow
one CONFIRM for confirm-all
straightforward proposals confirmed together
exception remains visible and unresolved
Advanced attribution tools remain reachable
routine multi-Subject ADD creates several Subjects atomically
```

The smoke is wired into `scripts/validate_repository.py` as:

```text
installed-wheel smoke: issue #106 Artifact attribution batching
```

so final repository qualification carries the same installed boundary.
