# Concord v0.3.0 Core Grouping-Signal Integration

**Status:** Implemented development baseline for issue #49
**Concord development version:** `0.3.0.dev0`
**Current Core requirement:** `pds-core>=0.6.1,<0.7`
**Exact qualification release:** `pds-core` v0.6.1

## Purpose

Concord v0.3 begins consuming Core's neutral `grouping_signal_set_v1`
interchange as an optional input to later teacher-approved GroupPlan workflows.
Issue #49 establishes the package, release-artifact, fixture, contract, privacy,
and dependency boundary only. It does not implement GroupPlan records or a
teacher-facing signal workflow.

The intended dependency/data direction is:

```text
optional producer
      |
      v
pds-core grouping_signal_set_v1
      |
      v
   Concord
```

The initial academic producer is expected to be Meridian:

```text
Meridian -> Core grouping_signal_set_v1 -> Concord
```

That arrow describes data flow through a Core-owned interchange. Concord does
not import Meridian, query Meridian's workspace, or require Meridian to consume
a conforming signal. Teacher-authored Core signals and signals from other
conforming producers are equally valid inputs.

## Public Core APIs

Concord consumes grouping signals only through the defining public Core
modules:

```python
pds_core.grouping_signals
pds_core.grouping_signal_csv
pds_core.grouping_signal_storage
pds_core.grouping_signal_diagnostics
```

Core remains the authority for:

- typed `GroupingSignalSet` values and subordinate models;
- strict structural validation;
- canonical JSON serialization and parsing;
- `grouping_signal_csv_v1` conversion;
- immutable exchange persistence;
- canonical-byte SHA-256 binding;
- class/roster diagnostics; and
- exact Core class/student identity.

Concord does not maintain a second grouping-signal model, JSON codec, CSV
parser, storage grammar, digest reader, or roster-comparison algorithm.

## Contract identity

The released contract is:

```text
contract name: grouping_signal_set_v1
schema_version: "1"
record_type: grouping_signal_set
```

A signal is an immutable snapshot for one Core class. Its logical identity is:

```text
(class_id, signal_set_id)
```

Materially changing its contents requires a different `signal_set_id`.
Version 1 has no revision chain, `latest`, `current`, `active`, or mutable head.
A later Concord workflow must select an exact signal explicitly rather than
choosing one by timestamp, filename, identifier ordering, or directory order.

## Canonical bytes and digests

Core canonical JSON remains the integrity authority. Core exchange persistence
binds those exact canonical bytes with SHA-256.

Two digest concepts must remain separate:

```text
source.snapshot_digest
    -> digest of an upstream producer/source snapshot when present

Core grouping-signal digest
    -> digest of the canonical grouping_signal_set_v1 bytes
```

Issue #54 signal-backed GroupPlans preserve the exact Core signal identity and
canonical digest for reproducibility. They do not substitute the producer's
`source.snapshot_digest` for the Core signal digest.

## Contextual ordinal bands

A dimension declares:

```text
dimension_id
band_count = N
```

and each represented student band is an integer in:

```text
1..N
```

The number is ordinal only within that exact signal set and dimension. It is
not a universal numeric interval and is not a:

```text
Grade
percentage
point value
rubric Score
proficiency category
mastery level
ability label
readiness label
behavior label
demographic label
permanent learner attribute
final grouping instruction
```

Concord must not attach labels such as `low`, `high`, `proficient`, or
`advanced` to Core band numbers as if they were contract semantics.

## Dimensions

One signal set may contain several independent dimensions. Concord does not:

- select the first dimension implicitly;
- average or combine dimensions;
- compare the same band number across separate dimensions; or
- infer that one dimension is academically stronger or more important.

Issue #53 provides explicit teacher selection and diagnostic presentation.
Issue #54 now consumes one explicitly selected dimension through that typed
selection boundary for the bounded signal-dependent planning strategies.

## Exact student identity and partial coverage

Entries use exact Core `student_id` values. Names, email addresses, roster
position, case folding, and fuzzy matching are not identity authorities.

Partial dimension coverage is valid. A missing `(student_id, dimension_id)`
means only that the selected signal has no band for that exact student in that
exact dimension. It does not mean zero, band 1, failure, absence, unenrollment,
or permission to omit the student from a plan.

Core diagnostics distinguish:

```text
class_mismatch
wrong_class_student
unknown_student
missing_student_signal
```

and provide matched per-band counts. These are factual diagnostics, not
planning-policy decisions. Issue #55 owns the explicit teacher decision when a
planning strategy encounters missing signal data.

## CSV boundary

Core owns `grouping_signal_csv_v1`. The CSV representation contains exactly one
selected dimension.

For a signal that already contains one dimension, a complete CSV can preserve
identity when every canonical value is preserved.

For a multi-dimensional source, exporting one dimension produces:

```text
dimension_projection
```

not another complete serialization of the source. Converting that projection
to a standalone signal requires a new explicit `signal_set_id` and aware
`created_at`. Concord must not silently reuse the original multi-dimensional
identity.

Teacher-facing discovery, inspection/diagnostics, and Core CSV import are
implemented by issue #53. A Concord-specific export format is not introduced.

## Immutable exchange storage

Core stores grouping signals in its neutral exchange namespace and owns the
path/digest rules. Concord uses Core's public storage services for exact load,
list, write/test setup, and digest verification.

The documented Core layout is:

```text
exchange/grouping-signals/<class_id>/<signal_set_id>.json
exchange/grouping-signals/<class_id>/<signal_set_id>.json.sha256
```

Concord does not reconstruct that path or open the sidecar directly in
production code.

Core semantics are:

```text
new immutable identity + bytes -> created
identical replay               -> existing
same identity + different bytes -> conflict
```

There is no automatic successor or mutable `latest` pointer.

Concord vendors the byte-exact synthetic fixture payload beneath:

```text

```

with provenance in:

```text
tests/fixtures/core_grouping_signals/PROVENANCE.md
```

The upstream `SHA256SUMS.txt` is preserved exactly. The fixture set contains:

```text

classes/english10_p2/roster.csv
classes/english10_p4/roster.csv

```

`.gitattributes` forces LF endings for the exact-byte subtree so Windows
checkout does not corrupt canonical fixture bytes.

`scripts/verify_core_grouping_fixtures.py` authenticates the vendored payload.
When supplied the released fixture ZIP, it also verifies the exact archive
filename, outer SHA-256, member set, internal manifest, member digests, and
byte-for-byte agreement with the vendored copy.

Fixture dimension names and band counts are test data only. They are not
Concord defaults or policy recommendations.

## Producer neutrality

`GroupingSignalSource.module_id` is provenance data, not runtime dispatch.

A signal with:

```text
source.kind = module_generated
source.module_id = synthetic_module
```

is consumed through Core without installing `synthetic_module`. The same rule
applies to a future Meridian-produced signal:

```text
source.module_id = meridian
```

does not authorize or trigger `import meridian`.

Concord production code has no Meridian runtime dependency, optional import,
plugin callback, source-workspace crawler, or private Meridian record reader.

## Privacy

A populated grouping signal is teacher-restricted educational data because it
contains class identity, student IDs, relative planning signals, and source
provenance even though raw academic values are excluded.

Grouping-signal values must not be copied by default into:

```text
logs or crash reports
passive attention summaries
PDS2 payloads
Route Registrations
packet or Artifact metadata
Score Records
Academic Result Manifests
Publication Records
```

The committed fixtures contain synthetic identities only. Routine validation
messages should identify structural categories and bounded identifiers/counts,
not dump student-band tables.

## Concord planning boundary

The grouping signal is optional planning input. It is not a GroupPlan, Group,
Membership, Score, or Grade.

```text
GroupingSignalSet != GroupPlan
GroupPlan != Group
GroupPlan != GroupMembership
band != Score
band != Grade
band != proficiency
missing signal != lowest band
```

Direct Group creation and membership management remain first-class without a
signal.

Issue ownership after #49 is:

```text
#50  GroupPlan records and lifecycle
#51  manual planning/direct arrangement import
#52  deterministic random planning
#53  signal discovery, import, dimension selection, diagnostics
#54  similar-signal and mixed-signal planners
#55  explicit missing-signal teacher decisions
#56  apply approved plans through native Group/GroupMembership services
```

Applying a later approved plan must not copy source band values into
`GroupMembership`.

## Non-goals of issue #49

Issue #49 does not add:

- GroupPlan records or persistence;
- signal discovery/import CLI or menu commands;
- grouping algorithms;
- automatic dimension selection;
- missing-signal placement policy;
- plan approval/application;
- Group or GroupMembership creation from signals;
- Meridian academic derivation;
- Concord Score-to-band derivation;
- Grade/proficiency calculation; or
- signal values in routing, packet, Artifact, result-manifest, or publication
  metadata.

The completed boundary is therefore:

```text
pds-concord 0.3.0.dev0
    -> pds-core>=0.6.1,<0.7
    -> public grouping_signal_set_v1 APIs
```

with Core owning interchange semantics and Concord retaining planning authority.
