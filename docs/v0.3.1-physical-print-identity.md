# Concord v0.3.1 Physical Print Identity

Issue #102 adds a human-readable recovery aid to newly generated routed Concord
Packet pages without changing Core, Concord, PDS2, or Template identity models.

## Printed fallback

New routed pages keep their exact existing Activity/Page recovery identity and add
the authoritative Core class ID:

```text
Concord <activity_id> page <artifact_page_id> | Class: <class_id>
```

When one exact Core student is already present in the Packet target context, the
same immutable fallback also includes a privacy-minimized roster-derived label:

```text
Student: <first_name> <last_initial>.
```

The short student label is derived from Core's structured `first_name` and
`last_name` fields. It does not replace `student_id`, `ParticipantReference`,
Artifact Author/Subject state, or any Score target.

Group, Activity, and teacher targets do not infer a student from membership or
other context.

## Authority boundary

Machine routing remains unchanged:

```text
PDS2 RouteLocator
    -> immutable Core RouteRegistration
    -> Concord ArtifactPage
```

The new text lives only in the existing human-readable fallback. Concord does not
add student data to the PDS2 payload or to route `module_details`.

The QR route is machine authority. The printed fallback is a teacher-visible
physical recovery aid.

## Deterministic replay and compatibility

The fallback is created only for newly generated pages and is persisted on the
canonical `ArtifactPage`, then exactly mirrored into
`RouteRegistration.human_fallback`.

Re-rendering consumes that stored immutable fallback. It does not look up the
current roster again. Consequently, a later roster-name change does not alter
the bytes of an already-generated Packet.

Existing v0.3.0 pages retain their historical fallback text and are not rewritten
or migrated. Existing retained scans, returned evidence, route identities,
Template Versions, Packet identities, and output digests remain valid.
